## Use Transactions for Multi-Step Operations

When multiple database operations must succeed or fail together, wrap them in a transaction. This prevents partial updates that leave your data in an inconsistent state. This rule says what every ORM must do; the code is in `db-typeorm-use-transactions` for TypeORM and `db-prisma-use-transactions` for Prisma.

- **Every query inside goes through the transaction.** A query through anything else (an injected repository, the client outside the transaction's callback) runs outside the transaction and commits on its own.
- **Joining another module's transaction.** A write to another module's data goes through that module's service (see `arch-data-access-in-services`). When it must join the caller's transaction, the other service's method takes the transaction as its first parameter and uses it for every query. The caller never touches the other module's tables.
- **Keep transactions short.** A transaction holds a pooled connection and its row locks until it ends, so a slow one starves the pool and blocks every writer of the same rows. Take the slow part out instead of raising a timeout.
- **A bulk write in chunks falls back to one row at a time for any row-level error.** A chunk written in one transaction fails whole when the database refuses one of its rows. The fallback then writes that chunk's rows one by one, each in a transaction of its own, for any error a row's own data causes: SQLSTATE class `22` (data exceptions, such as a value too long for its column or out of range) and class `23` (integrity constraints: unique, foreign key, not null, check). It records each refused row's failure with its reason and goes on with the next. A fallback for one code alone (a unique violation) lets any other refusal fail the whole chunk, and the import with it, with no row reported. Any other error (a lost connection, a conflict) still fails the chunk, for the job to try again.
- **Keep calls to external systems out** (payment providers, email, other services): they cannot be rolled back, and they hold the transaction and its locks open for a network round trip. Commit first, then call the provider, and record its outcome in a second write (or hand it to a queue, see `micro-use-queues`).
- **A call that changes something in an outside system (a charge, a transfer, a message sent) has distinct outcomes, and the record keeps them apart (see `di-liskov-substitution`).** Done. Rejected for this input: the row records it and the call is never sent again, while what it was for stays open for a new call with other input and an idempotency key of its own (for a payment, a declined card: the customer tries another card, and in the shop the order stays pending). Refused: the provider answered with a refusal and changed nothing, so the row records it and the call is never sent again, as it would fail the same way. Unknown (no answer, a 5xx, an answer the code cannot read): the row stays pending. With a provider that takes an idempotency key, as payment providers do, the call is sent again with the same key, each wait longer than the last, and only while the provider still keeps the key (see `micro-use-http-clients`); past that, a new send would be a new change (for a payment, a new charge). The row is then marked for a person to check at the provider and reported (see `error-report-to-sentry`), as it is at once with a provider that takes no key, such as a mail provider. Treating every failure as unknown sends a refusal again forever and leaves what it was for stuck; treating every failure as refused loses a change that went through, such as a charge.
- **When the outside system reports the outcome later**, the call is a pending row until it does. If what the call was for ends first, the call is canceled at the provider after the commit, retried from the row like any other call, so it cannot complete later. A result reported for something that already ended, or that another call already settled, is recorded in the same transaction with the compensating call it needs (a refund for a charge), and that call is sent after the commit: the record keeps every change that went through. A unique index that limits these calls per record covers only the statuses that hold the result or may still take it, so such a late result fits beside the one that holds it. In the shop, by its choice of flow: a card payment waits for the customer's 3-D Secure and is settled by the provider's notification (see `api-controller-conventions`); an order that is canceled or expires cancels its waiting payment; a charge reported for an order that another payment already holds, or that was canceled, is recorded as `refund_pending` and refunded after the commit; and the unique index allows one payment per order among those statuses.

**A change that depends on the current state is one conditional update.** Reading a row, checking it in code and then updating lets two requests both pass the check: two buyers take the last item in stock, an order is paid twice, a shipped order is canceled. This applies to every check on a value (a stock level, a balance) and to every state transition (paying, canceling or shipping an order, marking a notification read). Put the expected state in the criteria of one update (`quantity >= :quantity`, `status = 'pending'`) and act on the number of rows it changed. Read the row afterwards only to tell the caller why nothing changed: a 404 for a missing row, a 400 for the wrong state. When repeating a transition is harmless (marking a notification read), no changed row on an existing row is a no-op instead of an error, and the method returns the row as it is.

**A check the change depends on runs inside its transaction, under the lock, the caller's own state included.** When a change is allowed only while another row is in some state, and that row can change at the same moment, the check reads that row inside the change's transaction with `FOR UPDATE`, never before the transaction starts. The caller is such a row when a route refuses a caller in some state (see `security-auth-jwt`): two users who change each other's access at the same moment both pass a check made before their transactions, and both changes commit. Inside, each transaction locks both rows, the caller's and the target's, in id order (`SELECT ... FROM users WHERE id IN (:callerId, :targetId) ORDER BY id FOR UPDATE`), checks the caller on the locked row, then writes: the second waits for the first and sees what it wrote.

**An update writes only what the request changes, and only to a live row.** An update of a user's name or a product's price is one update statement too, with the fields from the request and, for a soft-deleted model, `deleted_at IS NULL` in its criteria. Read the row afterwards to return it, or to answer 404 when nothing changed. Loading a row, changing it in memory and saving it back writes the stale copy: a concurrent change to another field is lost, and with TypeORM a delete that landed in between is undone (see `db-typeorm-use-transactions`).

**Lock order.** Transactions that write the same rows take their locks in one order, or two of them wait for each other until PostgreSQL ends one with a deadlock (SQLSTATE `40P01`). A parent row comes first, then its children (in the shop, the order before its payments or items): a transaction that settles a payment locks the order row (`FOR UPDATE`) before it writes the payment, even when it updates the order last. Rows of one table are taken in the order of their key (in the shop, an order's inventory items by `sku`). Rows that several parents share are locked in one order of tables, fixed once for the app and the same in every transaction (in the shop, gift cards before inventory items, so canceling restores the gift card before it gives the stock back). A step written in another order is moved, not left to the deadlock detector. A deadlock that still happens is a conflict like any other: a transaction that locks rows other transactions also lock (a stock level, a balance) runs through the retry of the module that owns the database connection, which runs it again a few times, then answers 409. Its work only touches the database, since a call to another system in it would be repeated, and the global filter answers 409 for a conflict that reaches it unretried (see `error-use-exception-filters`).

**Isolation.** The default is the database's, `READ COMMITTED` on PostgreSQL. A conditional update is safe under it because the check and the write are one statement. That holds row by row: an update over a set of rows (every token of a session, every item of an order) sees only the rows committed when it starts, and misses a row another transaction is inserting into the set at that moment. Make one row stand for the set (the session, the order), update it on both sides, in the transaction that adds to the set and in the one that changes the set, and the second waits for the first on that row's lock (see `security-auth-jwt`). When correctness depends on a value read earlier in the transaction staying unchanged (a count checked against a limit, then an insert), lock the row the limit belongs to before counting: `SELECT … FOR UPDATE` on the product for its 8 images. Writers for one product then run one after the other, each counting what the previous one added, and writers for other products do not wait. When no row of this module stands for the set (a customer's limit of unpaid orders, where the user row belongs to the user module), take a transaction-level advisory lock keyed by the set before counting: `pg_advisory_xact_lock(hashtextextended('order-pending:' || user_id, 0))`. One customer's placements then wait for each other, the lock ends with the transaction, and nobody else waits. The key names its purpose, so two kinds of lock never share one. Not `SERIALIZABLE` for this: under it, a transaction that updates a row another one changed since it began fails, so two customers buying the same product at the same moment conflict on its stock, and while a table is small PostgreSQL tracks reads by index page, so transactions about unrelated customers conflict too. `SERIALIZABLE` is for a check over rows that no one key names. Retry the whole transaction a few times on a conflict, which PostgreSQL reports as SQLSTATE `40001` (serialization failure) or `40P01` (deadlock), on a query or on the `COMMIT`. When the retries run out, answer 409 (`ConflictException`), never let the database error become a 500. Every module that retries uses the same transaction service of that module (`DatabaseTransactionService` with TypeORM, `PrismaTransactionService` with Prisma), which recognizes a conflict and runs the transaction again.

Reference: [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
