## Module Structure
- [ ] Each feature has its own module owning its controllers, services, entities and DTOs; nothing is organized by technical layer at the app root (`src/controllers/`, `src/services/`) [arch-feature-modules]
- [ ] Every file of a module sits in a type folder, however few files it holds; only `{module}.module.ts` sits at the module root, apart from the two entry points Node runs (`sentry/preload.ts`, `cli/main.ts`); `src/` holds only `main.ts` and `app.module.ts` at its root; no `repositories/` folder and no `{module}.module-definition.ts` (a configurable module's options type in `types/`, its token in `constants/`, its builder in the module file with the token as `optionsInjectionToken`) [arch-feature-modules, arch-use-dynamic-modules]
- [ ] A file sits in the folder of its kind, with that kind's suffix: Nest middleware in `middlewares/` (`.middleware.ts`), command-line commands in `commands/` (`.command.ts`), storage adapters handed to a library (a cache store, the throttler's storage) in `stores/` (`.store.ts`, built with `new` in the module's options factory, so neither `utils/` nor providers), the app's subclasses of a queue library's worker and queue in `workers/` (`.worker.ts`) and `queues/` (`.queue.ts`) while the processors stay in their features' `processors/`, event payload classes in `events/`, `@OnEvent` handlers in `listeners/`, custom `class-validator` decorators in `validators/` [arch-feature-modules]
- [ ] Exported types are `type` aliases in `types/{name}.type.ts` and enums in `types/{name}.enum.ts`, one per file named after it; an `interface` only for a contract a class implements behind a token, in `interfaces/{name}.interface.ts`, one per file, and the data it passes around is a `type`; a type only its own file uses stays there, unexported [arch-feature-modules, di-use-interfaces-tokens]
- [ ] Exported constants and injection tokens sit in `constants/{name}.constant.ts`, one concern per file, with the module prefix. A value that sets behavior clients or operators see (a rate limit and its window, a session lifetime, a retention period) is exported from there even while one file uses it; a value that serves one file's implementation stays in that file, unexported and named for what it holds. `src/config/` has no `constants/`, so the bounds `validate-env.ts` checks stay in that file [arch-feature-modules, arch-resource-naming]
- [ ] `utils/` holds pure functions only (the module's own logic and rules, imported by its other files and tests, and directly by another module that needs one, such as the database module's error checks; never wrapped in a service just to be injected): nothing with a side effect (an SDK call, I/O) and no state, except a function that only wraps a call it is handed (`addJobInTime()` in `queue/utils/`); a function only its own file uses stays in that file, unexported, as a private method or a file-local function [arch-feature-modules, micro-use-queues]
- [ ] A class that calls an outside system (a provider's API, another service over HTTP or gRPC) sits in `clients/`, owns only the transport (the requests, the key, the timeouts, the raw answers) and is named for the system, not the module: `StripeClient` in `payment/clients/stripe.client.ts`; an AWS service's client also names the vendor, `AwsS3Client` in `storage/clients/aws-s3.client.ts`. Only the client calls the SDK, whose own client is a provider of the module injected by its class (`Stripe`, `S3Client`); a token only when the SDK exports no class to inject, so flag a token (`STRIPE_CLIENT`) only for an SDK whose client is a class [arch-feature-modules, arch-resource-naming, micro-use-http-clients]
- [ ] A class that puts one outside system behind the module's interface sits in `adapters/` as `{System}Adapter` in `adapters/{system}.adapter.ts` (`StripeAdapter`, `AwsS3Adapter`), on top of that system's client, which it calls in place of the SDK: it builds the system's requests from the module's types, checks every answer field by field in private methods (not `utils/`) and returns the module's shapes; it implements the module's interface (`PaymentAdapter`) and is bound to the module's token (`PAYMENT_ADAPTER`). A system behind two of the module's interfaces gets one adapter per role (`TwilioSmsAdapter`, `TwilioVoiceAdapter`); the next system adds a client and an adapter, not a module. The api module's `adapters/` also holds the app's subclasses of Nest's adapters (`ApiRedisIoAdapter extends IoAdapter`) [arch-feature-modules, arch-resource-naming, di-use-interfaces-tokens]
- [ ] A copied `.proto` sits byte-identical in `proto/`, at the path its owner keeps it, pinned by a unit test of its SHA-256, and an `assets` entry in `nest-cli.json` copies it into `dist/` [arch-feature-modules]
- [ ] `src/shared/` is a folder of plain files: no `SharedModule`, no services, controllers or entities. Each file is domain-neutral and used by two or more modules, or is one of the app-wide pieces, which are only `PaginatedResult`, `JwtUser` and the `Role` enum behind it; each sits in a type folder (`types/`, `utils/`, `constants/`, `errors/`) and is named for its concern, without a module prefix; nothing at the `shared/` root, no folder named for a feature (`shared/acl/`) or a kind of provider (`shared/services/`) [arch-shared-folder]
- [ ] No file in `src/shared/` imports from a module or from the ORM: what knows the database, its transactions and its error codes belongs to the module that owns the connection (`database/` with TypeORM, `prisma/` with Prisma). No DTO, decorator, validator, filter or interceptor in `shared/`: one that works the same for every module is the api module's (`ApiPaginationQueryDto`, `@AuthUser()`, `@IsStorableDate()`), one about a module's data (`OrderAddressDto`) stays in that module [arch-shared-folder]
- [ ] The api module (`src/api/`) holds only what works the same for every module (the global filter and interceptors, the decorators controllers use, the pagination query DTO, `ApiRequest`); a DTO of one module's data never moves there, even when other modules nest or extend it, and no service imports from the api module: what a service needs (`PaginatedResult`, `JwtUser`) stays in `shared/` [arch-shared-folder]
- [ ] A file added to or moved into `src/shared/` has a second consumer in the change (the root wiring files and the api module count as consumers, so a domain-neutral helper the global filter and one feature module both use stays in `shared/`); one that drops back to one consumer moves back to that module, and one nothing uses is deleted. Flag only files the change adds or moves [arch-shared-folder]
- [ ] A module exports services only (its pure functions in `utils/` are imported directly, never registered as providers): another module injects `PaymentService`, never `PAYMENT_ADAPTER`, an adapter, a client, or a third-party module the owner configured (`JwtModule`, `HttpModule`), which the owning module wraps in a service of its own. The exceptions are the app's own configurable module, re-exported by the one module that configures it, and a connection a library takes raw (`REDIS_CLIENT`, as `DataSource` is shared), used by those libraries alone [arch-module-sharing]
- [ ] An injectable used by several modules is provided and exported once, by its own module named for what it does (`storage/` exporting `StorageService`), never listed in several modules' `providers` [arch-module-sharing, arch-shared-folder]
- [ ] One client per outside system: two modules that call the same system share one capability module (one client, one mapping of its failures), and a second copy of a client is a **Warning** even when the two store different kinds of files; the capability module's service speaks its consumers' terms (`StorageFolder.ProductImages`) and its adapter maps them to the system's names (the bucket, the folder's prefix) [arch-module-sharing]
- [ ] Files live in the environment's one private bucket, a folder (key prefix) per kind of file; environments never share a bucket; public files go out through a CDN and private ones through a short-lived presigned URL, never a public bucket or object ACL; a second bucket only for a setting the provider applies to a whole bucket (Object Lock, another region) [micro-use-http-clients]
- [ ] Every Redis connection the app opens itself (the commands' client, the subscriber, the Socket.IO adapter's pair) is built and closed by the `redis` module; app code publishes, subscribes and pings through `RedisService`, never `new Redis()` of its own or an injected `REDIS_CLIENT` [arch-module-sharing]
- [ ] No custom `@Global()` module, no `isGlobal` option on the app's configurable modules, and no catch-all `CoreModule`, `CommonModule` or `SharedModule`; only third-party infrastructure is global (`ConfigModule`, the logger module, `ClsModule`, `CacheModule`, `NestjsFormDataModule`), each registered once, in `AppModule` or in the app's one module for that infrastructure, which `AppModule` imports (`LoggerModule`, `SentryModule`) [arch-module-sharing]
- [ ] No circular module dependency. The cycle is broken by a third module named for what both need (never a `SharedModule`), by an event, or, when an inbound controller causes it, by moving that controller to the module whose service it calls (`OrderInternalController` in `order/`); `forwardRef()` only as a last resort, with a comment saying why the cycle cannot be broken [arch-avoid-circular-deps]
- [ ] Singular resource name for the module folder and the module, controller, service and entity classes, their files and injected properties (`src/order/`, `OrderModule`, `OrderController`, `OrderService`, `Order`); plural only in the URL and the table; an uncountable noun keeps its form (`analytics/`) [arch-resource-naming]
- [ ] Every class, type, enum, exported constant and file a module declares starts with the module name, once (`OrderItem`, never `Item` or `OrderOrderItem`; `OrderPricingService`, `CreateOrderItemDto`, `OrderStatus`, `ORDER_CANCELABLE_STATUSES`), in a capability module too (`AuthSessionService`, `AuthJwtGuard`, `HealthShutdownService`, and the api module's `ApiExceptionFilter` and `API_VALIDATION_PIPE_OPTIONS` in `api-` files); a property injecting one of the module's own classes takes the prefix (`orderItemRepository`), other dependencies are named for their class (`paymentService`, `dataSource`). Flag only names the change adds or changes, as Warnings; existing names elsewhere are not findings, and a rename of existing names inside an unrelated change is one [arch-resource-naming]
- [ ] The only names without the module prefix: plain functions and decorators (`calculateOrderTotal()`, `@AuthUser()`); a client or adapter of an outside system, named for that system (`StripeClient`, `StripeAdapter`, `AwsS3Client`); a test double, named `Fake{Interface}` (`FakePaymentAdapter`); file-local constants, named for what they hold; a param DTO for a route that nests the module's resource under another module's, named for the route, parent first (below); and the files of `src/shared/` and `src/config/`. The interface an adapter implements keeps the prefix and ends in `Adapter`, never `Interface`: `{Module}{Role}Adapter` behind `{MODULE}_{ROLE}_ADAPTER` (`NotificationEmailAdapter` behind `NOTIFICATION_EMAIL_ADAPTER`, `PaymentAdapter` behind `PAYMENT_ADAPTER`) [arch-resource-naming]
- [ ] Everything in `services/` is a service: its class ends in `Service` and its file in `.service.ts` (`UserPasswordHasherService`, never `UserPasswordHasher` in `user-password-hasher.ts`); other injectables are named for their kind and sit in that kind's folder (`OrderOwnerGuard` in `guards/order-owner.guard.ts`) [arch-resource-naming]
- [ ] Listeners: one class per source module, named `{Module}{Source}EventsListener` (`OrderPaymentEventsListener` in `order/listeners/order-payment-events.listener.ts`) with one `on{Event}()` method per event (`onPaymentCaptured()`); a module listening to its own events uses `{Module}EventsListener` [arch-resource-naming]
- [ ] Internal-route classes put `Internal` right after the module name (`OrderInternalController` for `/internal/orders`; DTOs keep the verb first, `CreateOrderInternalDto`). The module folder carries the resource's full name and nothing in it uses a shorter or longer variant (`GiftCard` in `gift-card/`, never `card/` or `voucher/`). A sub-resource keeps the prefix in code and table and drops it in the URL under its parent (`OrderItem`, `order_items`, `/orders/:id/items`), keeping it under another module's route (`/orders/:id/payment-refunds`); one whose names pass three words, or that other modules use on its own, becomes its own module [arch-resource-naming]
- [ ] A query or param DTO used only in its module takes the module prefix (`OrderSortQueryDto`); one reused by several modules stays in the module whose data it describes, with that prefix, and the others import it from there; only a piece about no module's data (pagination) is the api module's, with the `Api` prefix; a param DTO for a route that nests this module's resource under another module's is named for the route, parent first (`OrderShipmentIdParamDto` in `shipment/` for `/orders/:id/shipments/:shipmentId`) [arch-resource-naming]
- [ ] A route starts with its module's name, in the plural for a resource module (`/orders`) and as the capability for a capability module (`/auth/login`, `/health/live`); the one exception is a provider's callback, `POST /{provider}/events` (`/stripe/events`), named for the provider whatever module serves it [arch-resource-naming]
- [ ] Relative imports inside a module, the root files (`app.module.ts`, `main.ts`) included; the `@/` alias with the module name first across modules (`@/payment/services/payment.service`); never `../../sibling`, never the alias for the importing module's own files [arch-import-boundaries]
- [ ] What describes another module's data or rules, its DTOs and types included, is imported from that module with the alias: never copied, and never moved to the api module or `shared/` because a second module uses it; only a domain-neutral helper moves to `shared/` once a second module needs it [arch-import-boundaries, arch-shared-folder]
- [ ] `tsconfig.json` declares the alias in `paths` without `baseUrl` (TypeScript 6 rejects it); in an ESM project (`"type": "module"`) relative and `@/` imports end in `.js` [arch-import-boundaries, references/project-setup]
- [ ] Types used in decorated signatures (`ConfigType`, `Relation`, interfaces) are imported as types (`import type`, `import { type Relation }`), in CommonJS and ESM alike, while a class Nest injects stays a value import; `tsconfig.json` keeps `strictPropertyInitialization: false` on TypeScript 6 [references/project-setup]
- [ ] A module reused across apps or instantiated more than once takes its configuration as typed options: `forRoot` and `forRootAsync` generated by `ConfigurableModuleBuilder`, never a hand-written, sync-only `forRoot` or a string options token; it never imports from `src/config/`, injects `ConfigService` or reads `process.env`, and the app maps its namespace into the options in `forRootAsync` (a module used by one app only may inject its namespace) [arch-use-dynamic-modules]
- [ ] A configurable module of the app's own (`MailModule`) is configured once, in a module that re-exports it, never in `AppModule` [arch-use-dynamic-modules]
- [ ] A reusable module takes what it needs from the app through its options (a `getRequestId` function the app maps to its request context), never by importing a library the app happens to use, such as `nestjs-cls`: `@Optional()` covers a missing provider, not a missing package [arch-use-dynamic-modules]
- [ ] Recurring per-instance work runs from the one `scheduler/` module, imported only by `AppModule` next to `ScheduleModule.forRoot()`: `SchedulerService` holds only the timing, one `@Interval` method per job (never `@Cron`), each calling the feature service's method that does the work and catching its errors; no timer inside a feature's service [arch-feature-modules]
- [ ] A `scheduler/` job skips a run while its previous run is still going, and works on the instance's own state or gives the same result however many instances run it; work that must run once across instances, or must not be skipped by a restart, is a BullMQ job scheduler instead [arch-feature-modules]
- [ ] A command line is the `cli` module: `cli/main.ts` picks the command from the arguments and runs it on `NestFactory.createApplicationContext(CliModule)`, closed in a `finally`; `CliModule` loads `ConfigModule.forRoot()` with `AppModule`'s `load` and `validate`, `LoggerModule` and the feature modules its commands call, without the HTTP server, the queue workers or the schedule; it starts through Sentry's preload (`node --import ./dist/sentry/preload.js dist/cli/main.js <command>`) from a `package.json` script [arch-feature-modules]
- [ ] Each command is a provider in `cli/commands/` named for what it does (`CliCreateAdminCommand` in `cli-create-admin.command.ts`), calls a method of the feature's service, and validates its input with the request DTO the route would use and the same validator options (`API_VALIDATION_PIPE_OPTIONS`); a secret comes piped on standard input, never as an argument [arch-feature-modules]
- [ ] An operator's mistake (a usage error, input the DTO refuses, a 4xx the service throws) prints its message on stderr and sets `process.exitCode = 1`; thrown out of `cli/main.ts`, it reaches the crash handlers, which print the alert marker and send a Sentry event. Any other error is rethrown as a crash [arch-feature-modules]

## Controllers
- [ ] Controllers are thin: they bind and validate input, call one service (their module's, or the user module's for `GET /auth/me`) and return its result; no business logic, and no repository, `DataSource` or query in a controller [api-controller-conventions, arch-data-access-in-services]
- [ ] Route paths are plural kebab-case nouns (`@Controller('orders')`, `@Controller('orders/:id/items')`); the resource's own id is `:id` and ids below it `:{child}Id`; no trailing slash, file extension or verb, except action segments on `POST`, `GET /:id/download` and the authentication flows [api-controller-conventions]
- [ ] Every route addresses an item by `:id`, and `/me` exists only as `GET /auth/me`; any other address exists only when the spec asks for it, and two routes of one method never take different keys in the same place [api-controller-conventions]
- [ ] The authentication flows are served by one controller of the auth module, each a `POST` named for its flow (in the shop, `/auth/login`, `/auth/refresh`, `/auth/logout`) with a handler of the same name, and `findMe` for `GET /auth/me`; no other route uses a verb. The same controller serves `GET /auth/me`, the caller's account read through the user module's service; no other module has a `/me` route [api-controller-conventions, api-use-dto-serialization]
- [ ] At most 4 collections deep, counting the root; anything deeper is a top-level collection filtered by its parent. A nested route checks that the child belongs to the parent and answers 404 when it does not [api-controller-conventions]
- [ ] Filters, sorting and pagination are query parameters, never path segments (`/orders?status=paid`, not `/orders/paid`); `POST /{resources}/search` only for criteria that do not fit a query string [api-controller-conventions]
- [ ] Method semantics: `GET` is safe whatever its last segment (`/:id/download` changes no state); `POST /{resources}` creates with a server-assigned id; `PUT` is an idempotent create-or-replace at a known target, and a repeat never creates a second resource (it returns the existing one or a documented error such as 409); `PATCH` changes plain fields only; `DELETE` is idempotent [api-controller-conventions]
- [ ] State transitions are `POST /:id/{verb}` actions, with a body only when the action has inputs, never a `status` field in a `PATCH` body. An action on the collection (`POST /{resources}/{verb}`) stores nothing: a check or dry run of a create, taking the create's body, or what a browser needs to reach the API, such as a session cookie [api-controller-conventions]
- [ ] Status codes are explicit where Nest's default differs: `@HttpCode(HttpStatus.OK)` on actions, on an item or on the collection, and on `POST .../search`; `@HttpCode(HttpStatus.ACCEPTED)` when the work is queued; `@HttpCode(HttpStatus.NO_CONTENT)` on `DELETE`, on an action with nothing to return, on a collection action that answers only a header or a cookie, and on a `PUT` that creates nothing a client reads back (a new password) [api-controller-conventions]
- [ ] A creating `PUT` answers 201 or 200 per call through `@Res({ passthrough: true })` and `httpAdapter.status()`, still returning the resource so the interceptors and the serializer run; never `@Res()` with a hand-built reply [api-platform-agnostic, api-controller-conventions]
- [ ] Handler names: `findAll`, `findById`, `findAll{SubResources}`, `create`, `update` (PATCH), `replace` (PUT), `upsert` or `create{Thing}` (idempotent PUT creation), `delete`, `search`, `download`, or the action's verb; a singular sub-resource adds its name (`replaceShippingAddress`) [api-controller-conventions]
- [ ] Parameter order: `@AuthUser() authUser: JwtUser` first, then `@Param()`, then `@Query()` or `@Body()`, then optional extras. The caller is never read from `@Req()`; other request context gets a param decorator of its own, built with `createParamDecorator` [api-controller-conventions, api-custom-param-decorators]
- [ ] `@Param()`, `@Query()` and `@Body()` are bound to DTO classes: no inline extraction (`@Param('id', ParseUUIDPipe)`, `@Query('limit', ParseIntPipe)`) and no manual check in the handler. Conversions live in the DTO (`@Type()`, `@Transform()`); a custom `PipeTransform` only for an argument that is not a DTO [api-use-pipes]
- [ ] Service results are returned directly: no `{ data }`, `{ success }` or other wrapper built in a controller or a service [api-use-interceptors]
- [ ] Decorator stacks repeated across routes are composed with `applyDecorators`, carrying metadata and Swagger decorators, never `UseGuards`: the auth guards are global and would run twice [api-custom-param-decorators]
- [ ] A provider's callback is `POST /{provider}/events` (never in an item's slot, such as `/orders/payment-webhook`), `@Public()`, `VERSION_NEUTRAL`, out of Swagger (`@ApiExcludeController()`) and rate limited on its own; it checks the provider's signature over the raw body (`rawBody: true` in `NestFactory.create()`), is idempotent by the event's id and answers 2xx for an event it already handled or does not act on [api-controller-conventions, security-rate-limiting]
- [ ] A new version only for a breaking change (an additive change ships unversioned), through Nest's URI versioning enabled in `ApiModule.setup()`: no hand-written `v1/` in a path, no second strategy, no `if (version === ...)` in a service. The new version's controller (`UserV2Controller` in `user-v2.controller.ts`) holds only the changed routes, with response DTOs of its own; routes outside the client contract (probes, webhooks) are `VERSION_NEUTRAL` [api-versioning]
- [ ] Versioning turned on in an API that started unversioned uses `defaultVersion: [VERSION_NEUTRAL, '1']`, so every existing path keeps answering. A version that ships joins `defaultVersion`, and only the changed routes are pinned: the new controller to its version, each changed route's old handler to the versions it still serves. A `@Version` on an unchanged handler or controller is a finding: it replaces the default instead of adding to it, so `@Version(['1', '2'])` there drops the unversioned path [api-versioning]
- [ ] A deprecated version sends `Deprecation` in RFC 9745's date form (`@` and the seconds since the epoch, never `true`), `Sunset` as an HTTP date and a `Link` to a real URI (`rel="deprecation"`, no `{id}` template), set by an api module middleware for that version's paths, matched on the request's `originalUrl` after the global prefix (`/api/v1/`), so a guard's 401, 403 or 429 and the body parser's 400 carry them too; `@Header()` reaches only the route's own answers. The version's operations are `deprecated: true` in the docs [api-versioning]

## Swagger / OpenAPI
- [ ] Every controller has exactly one `@ApiTags`, named after the resource, and its security decorator (`@ApiBearerAuth('bearer')`); no dev-only auth scheme is documented, and a public route of the controller says in its description that it needs no token [api-document-with-openapi]
- [ ] Every endpoint has `@ApiOperation` with `summary` and `description` [api-document-with-openapi]
- [ ] Every handler that returns a body documents its success inside the envelope with `@ApiEnvelopedResponse(X)` (one object, or `isArray: true`) or `@ApiPaginatedResponse(X)`, from `api/decorators/`; never a plain `@ApiOkResponse({ type: X })`, and never no decorator, since the CLI plugin then documents the bare return type. A `204` takes `@ApiNoContentResponse()`. `X` is the response DTO, or the entity the handler returns [api-document-with-openapi]
- [ ] Endpoint-specific error statuses are documented (`@ApiNotFoundResponse`, `@ApiConflictResponse`, `@ApiBadRequestResponse`, `@ApiForbiddenResponse`), each saying when it happens; recommended, so a missing one is a Suggestion [api-document-with-openapi]
- [ ] Every new or changed DTO field (create, update, query, param) has an explicit `@ApiProperty`, or `@ApiPropertyOptional` for a field declared with `?` or `@IsOptional()`, each with `description` and `example`; a nested-DTO field and a file field (`type: 'string', format: 'binary'`) take no example of their own. The CLI plugin does not run in the test runner, so it never replaces the decorators; it stays in `nest-cli.json` [api-document-with-openapi]
- [ ] `@ApiProperty` does not repeat `type`, `required`, `format` or `enum` that a validator already gives [api-document-with-openapi]
- [ ] Examples are realistic and self-explanatory, never placeholders (`'string'`, `123`); UUID examples are the nil UUID; dates are a fictional, valid ISO 8601 timestamp [api-document-with-openapi]
- [ ] Long descriptions are split with `'...' +`, not template literals [api-document-with-openapi]
- [ ] A response field only some callers get is `@ApiPropertyOptional`, its description saying who gets it; a route that answers a smaller shape to other callers documents both shapes (`oneOf`) [api-document-with-openapi]
- [ ] The `DocumentBuilder` sets no `servers` when the app has a global prefix; the spec is exposed wherever clients need it, never hidden behind `NODE_ENV` [api-document-with-openapi]

## Services
- [ ] Single responsibility: each service owns one domain concern; a name with "And" in it, a constructor with dependencies from many modules, or methods that share no state are the signs. The service that owns a use case orchestrates it, calling the other modules' services or emitting an event for side effects that need not succeed together (through the outbox when the side effect must eventually happen); a controller that calls several services to run a flow is the same finding [arch-single-responsibility]
- [ ] Constructor order: repositories (`@InjectRepository`, own module's entities) or `PrismaService`, then other services and token-injected abstractions, then configuration (`ConfigService` or a namespace injected with `@Inject(xConfig.KEY)`), then `DataSource` (none with Prisma); every dependency `private readonly`, without a `_` prefix [arch-service-conventions]
- [ ] Method parameters: the authenticated user (`authUser: JwtUser`) first when the method acts for a caller, then identifiers, the data DTO, optional parameters; a method no caller scopes (an admin delete, another module's lookup by id) starts with the identifiers [arch-service-conventions]
- [ ] No `static readonly` constants on a service: constants live outside the class in `UPPER_SNAKE_CASE`, exported from `constants/` with the prefix when clients see their effect, otherwise a `const` at the top of the file [arch-service-conventions]
- [ ] Shape validation (types, formats, required fields) in DTOs; services enforce only what the domain knows: whether a resource exists, whether the caller owns it, whether a state transition is legal [arch-service-conventions]
- [ ] Services throw typed exceptions and never return error objects for the controller to inspect: `NotFoundException` for a missing or not visible resource, `BadRequestException` for invalid input or a broken domain rule (an illegal state transition, insufficient stock), `ForbiddenException` for an action a rule forbids the caller on a resource it can see, `ConflictException` for a clash with existing data (a duplicate, a concurrent change). A domain error class (`EntityNotFoundException` in `shared/errors/`, which the global filter maps to its status) only for a service whose callers outside HTTP must tell errors apart by type (a queue processor deciding whether to retry); a service the command line shares with the API keeps throwing `HttpException`s, whose status the command line reads [arch-service-conventions, error-throw-http-exceptions]
- [ ] A service reads and writes only its own module's data: TypeORM repositories injected with `@InjectRepository` for the entities in its module's `TypeOrmModule.forFeature()`, or with Prisma its own module's delegates on `PrismaService` (`this.prisma.user` in the order module is a finding); another module's data goes through that module's exported service. No custom repository class (`OrderRepository` wrapping `Repository<Order>` or `this.prisma.order`); queries live in the service method that needs them, a large one in a private `_build...Query()` (`_build...Where()` with Prisma) [arch-data-access-in-services]
- [ ] Event names are `{object}.{action}`, lowercase and dot-separated, the action in the past tense (`order.created`), `_` in a multi-word object (`order_item.added`); the emitting service knows no consumer, and each consumer listens in its own module [arch-use-events]
- [ ] Work that must succeed or fail together with the write (reserving stock, counting the units sold) is called by the owning service inside its transaction, never left to a listener; a counter kept by listeners of two events (one adds, one subtracts) drifts, since listeners run in no guaranteed order, each in its own transaction [arch-use-events, db-use-transactions]
- [ ] A side effect that must eventually happen (a mail, a webhook delivery, telling another service) is written to the outbox in the change's own transaction (`OutboxService.add(manager, name, payload)`) and dispatched after the commit, never emitted by the producer after the commit; its listeners use `@OnOutboxEvent()` (`@OnEvent` with `async: true`, `promisify: true` and `suppressErrors: false`), throw on failure, and record their work under a unique key so a second dispatch does nothing more [arch-use-events]
- [ ] The outbox dispatcher claims only the event names this release has `@OnOutboxEvent()` listeners for, collected at startup, so an older instance never marks a newer event dispatched with no consumer; a side effect that moves to another consumer keeps one duplicate key across the release that moves it (the new consumer inserts the old consumer's key with `ON CONFLICT DO NOTHING` and acts only when it inserted it) [arch-use-events]

## DTOs and Validation
- [ ] Every body, query and param is a DTO class validated with `class-validator`, no `any` in a DTO or a handler signature; one global `ValidationPipe`, registered in `ApiModule.setup()` with `API_VALIDATION_PIPE_OPTIONS` (`whitelist`, `forbidNonWhitelisted`, `forbidUnknownValues`, `transform`); never `enableImplicitConversion`: numbers and dates are converted with `@Type(() => Number)` and `@Type(() => Date)` [security-validate-all-input, api-use-pipes]
- [ ] Every nested object, optional or required, has `@IsObject()`, `@ValidateNested()` and `@Type(() => Child)`, and a nested array `@IsArray()`, `@ValidateNested({ each: true })` and `@Type()`. A nested DTO has no field named `push`: class-transformer then builds an array sent for it as an instance of the class, a 500 for `[1]` and a pass for `[]` [security-validate-all-input]
- [ ] Every field is bounded: `@MaxLength` on every string, `@ArrayMaxSize` on every array, `@Max` on every number (page size and offset included), the api module's `@IsStorableDate()` on every date, and `@MaxFileNameLength()` on an uploaded file's name that is stored, logged or returned; an unbounded value reaches the database and comes back as a 500 [security-validate-all-input, api-file-uploads]
- [ ] A string stored in a `varchar(n)` column takes `@MaxCodePoints(n)` in place of `@MaxLength(n)`: `@MaxLength` counts a variation selector after a character as nothing, so text within it can still be too long for the column, a 500 [security-validate-all-input]
- [ ] Ids use `@IsUUID()` (any version); a URL the server will call is `@IsUrl({ protocols: ['https'], require_protocol: true })`; passwords take `@MinLength(12)` and `@MaxLength(128)` and never a `@Transform` [security-validate-all-input]
- [ ] An optional body field over a NOT NULL column refuses `null`: `@ValidateIf((dto, value) => value !== undefined)` in place of `@IsOptional()`, which lets `null` through on every optional field, or `{ skipNullProperties: false }` on a `PartialType` body DTO; a `null` reaching the column is a 500. A field the client may clear is nullable in the entity, with its own `@ValidateIf((dto) => dto.field !== null)`; query DTOs need neither [security-validate-all-input, api-use-mapped-types]
- [ ] Input DTOs are derived with `PartialType`, `PickType`, `OmitType` and `IntersectionType` from `@nestjs/swagger` (`@nestjs/mapped-types` in a project without Swagger), the key lists `as const`: a Create DTO's fields are never declared again in its Update DTO, and fields that must not change after creation are omitted. The body of a check of a create (`POST /{resources}/{verb}`) extends the create DTO [api-use-mapped-types, api-dto-naming]
- [ ] File and class names follow the DTO table: bodies start with a verb (`create-`, `update-`, `cancel-`, `search-`; never a `-request` suffix), params are `{resource}-id.param.dto.ts` named for the deepest resource (a dot, never `-param`), one endpoint's query is `{verb}-{resources}.query.dto.ts` (`find-all-` for a list), a response is `{resource}-response.dto.ts`, an internal route's body ends in `-internal.dto.ts` [api-dto-naming]
- [ ] A param DTO extends the shorter route's param DTO, so each parameter is declared once; a list query and a search body extend `ApiPaginationQueryDto` [api-dto-naming]
- [ ] A nested input shape used by one DTO stays in that DTO's file; one that several DTOs use is `{module}-{shape}.dto.ts` in the `dtos/` of the module whose data it describes (`OrderAddressDto` in `order/dtos/`); the api module's `dtos/` and `validators/` hold only what works the same for every module (`ApiPaginationQueryDto`, `@IsStorableDate()`, `@MaxCodePoints()`, `@MaxFileNameLength()`) [api-dto-naming, arch-shared-folder]
- [ ] A search body keeps every criterion optional, caps every array with `@ArrayMaxSize`, nests ranges (`{ min, max }`, `{ from, to }`) in its own file, and whitelists sort fields with `@IsIn`, which the service maps to columns, never interpolating a client string into SQL [api-dto-naming]
- [ ] A lookup by a secret value (a gift card code) takes it in the body, required, answers at most one match without paging, and is rate limited like a login [api-dto-naming, security-rate-limiting]
- [ ] Uploads go through `nestjs-form-data`, registered once (global, `MemoryStoredFile` storage): every upload route uses the api module's `@ApiFormDataRequest(options)`, which takes the route's form-data options (its `limits`), so a body without a boundary is a 400, not a 500; never `FileInterceptor` with `@UploadedFile()` or `ParseFilePipe`, which validate the file apart from the DTO. The route's `limits.fileSize` is twice the allowed size, and the real limit, with a message that names it, is `@MaxFileSize(max, { message })` [api-file-uploads]
- [ ] A file field is typed with a type of the module's own (a `Pick` of `MemoryStoredFile` in `types/`, whose comment links the Swagger plugin issue and says when to remove it), documented `@ApiProperty({ type: 'string', format: 'binary' })` and validated with `@IsFile()`, `@MaxFileSize()` and, for a format with a signature, `@HasMimeType()`. A JSON multipart field is parsed by a `@Transform` that keeps invalid JSON as the raw string for its validator to refuse; a `JSON.parse` that throws is a 500 [api-file-uploads]
- [ ] Upload routes have a rate limit of their own; the file is stored before its row (and deleted again when the row cannot be added) and deleted before its row; a soft-deleted record's files are deleted after a retention, by a method of the module's service that the `scheduler/` module calls on an interval; files served with a long cache lifetime are documented in the API docs as staying in caches after removal [api-file-uploads]
- [ ] An image other users see is re-encoded on the server (`sharp`: a pixel limit before decoding with `limitInputPixels`, any crop, a resize, no metadata kept), and a declared width or height is checked before an `integer` column stores it [api-file-uploads]
- [ ] An uploaded text file (CSV) is checked by a strict decode (`new TextDecoder('utf-8', { fatal: true })`) and its header, since `@HasMimeType()` trusts the client's `Content-Type` for a format without a signature; its reader stops at the row limit plus one, refuses a record wider than the header at its first extra field and cuts fields with `slice()`, never `field += char` (or a streaming parser given the same limits, `csv-parse` with `to_line` and `max_record_size`); a unit test reads a file of the shortest rows at the byte limit, and one of a single field, under a heap limit [api-file-uploads]

- [ ] **Critical:** no value the server can know comes from the request: a body carries what the client chooses (what it buys, how many), never a price, total, discount, balance or the caller's id; the service reads those from its own data (the caller from `@AuthUser()`) [security-validate-all-input]

## Entities and Serialization
- [ ] TypeORM entities carry persistence decorators only, plus `@Exclude()` and `@ApiHideProperty()` together on a column kept out of both the response and the OpenAPI schema; never `@ApiProperty` or `@Expose` on an entity [api-use-dto-serialization, db-typeorm-schema-conventions]
- [ ] **Critical:** every column that must not leave the service (`passwordHash`, a token hash, `deletedAt`) has `@Exclude()`, with `@ApiHideProperty()` next to it; a column added to a returned entity comes with that decision. `@Exclude()` without `@ApiHideProperty()` keeps the value out of the response but lists the column in the OpenAPI schema: a Warning [api-use-dto-serialization]
- [ ] Returning an entity is fine (do not flag it by itself); a response DTO with `@Expose()` fields is used where the shape differs: computed fields, a subset, nested projections, role-dependent fields as serialization `groups`, or a public contract [api-use-dto-serialization]
- [ ] **Critical:** an entity turned into a response DTO (`@SerializeOptions({ type })` or `plainToInstance()`) uses `excludeExtraneousValues: true`; otherwise every column, hidden ones included, is returned [api-use-dto-serialization]
- [ ] **Critical:** `@SerializeOptions({ type })` only on a handler returning one object or an array; on a paginated handler it converts the `PaginatedResult` wrapper (with `excludeExtraneousValues: true` the page arrives as `data: {}`; without it the items are never converted to the DTO). A page of response DTOs is converted item by item in the service, or in each version's controller once the versions return different DTOs [api-use-dto-serialization, api-versioning]
- [ ] A response DTO declares its own fields with `@Expose()`; never a mapped type of a Create DTO, which copies its validators and `@Transform`s and, with `excludeExtraneousValues: true`, serializes to `{}` [api-use-mapped-types]
- [ ] Request bodies are never bound to an entity or a Prisma input type, and entity fields are never spread by hand into an ad-hoc response object; a body bound to an entity or a Prisma input type (`@Body() user: User`, `@Body() data: Prisma.UserCreateInput`) is **Critical**: it skips the request DTO's validation and lets a client set any column (`isAdmin`), with Prisma relations included [api-use-dto-serialization]
- [ ] Entities returned to a client are class instances: `create()` for new rows, the row read after an `update()` for updates, never `save({ ...entity })` or `manager.save(Entity, { ... })`, which return plain objects that skip `@Exclude()`. **Critical** when a sensitive column such as `passwordHash` leaks this way [api-use-dto-serialization]
- [ ] A public response never carries another user's internal id (in the shop, the author of a review): it exposes only the fields the product chose to show, and caller-relative facts (such as an `isOwn` flag) are computed on the server [api-use-dto-serialization]
- [ ] Prisma: every route that returns data has a response DTO, converted with `excludeExtraneousValues: true` (`@SerializeOptions({ type, excludeExtraneousValues: true })` on a handler returning one object or an array, `plainToInstance()` per item in the service for a page), since Prisma returns plain objects, on which `@Exclude()` does nothing; **Critical** when converted without `excludeExtraneousValues: true` [api-use-dto-serialization]
- [ ] Prisma: a service returns the type the global omit leaves (`UserRecord`, a `Prisma.UserGetPayload<{ omit: typeof PRISMA_OMIT.user }>`), a method that takes `tx` included, never the generated model type; result shapes come from the generated client (`Prisma.OrderGetPayload`), never a hand-written copy [api-use-dto-serialization, db-prisma-avoid-n-plus-one]

## Dependency Injection
- [ ] Dependencies arrive through the constructor as `private readonly`: no `@Inject()` on a field and no `new` of an injectable class. `new` only for `new Logger(Class.name)`, the global pipes, filter and interceptors `ApiModule.setup()` registers, a per-route enhancer with constructor arguments (`new ApiTimeoutInterceptor(...)`), a library object a module's options take as an instance, built in its `useFactory` from injected values (`new ApiThrottlerStore(redis)`), and a provider built in a factory from an optional provider the factory injects [di-prefer-constructor-injection]
- [ ] An optional dependency is a constructor parameter with `@Optional()`; a subclass of a provider with `@Optional()` parameters declares its own constructor that repeats the marker and passes the value to `super()`, since NestJS 12 does not inherit it (`UnknownDependenciesException`) [di-prefer-constructor-injection]
- [ ] Optional infrastructure (a provider only some deployments have) is a module imported through `ConditionalModule.registerWhen()` from `@nestjs/config`, its condition a function in `src/config/` beside its namespace (`isSmsApiConfigured(env)` in `sms-api.config.ts`); consumers take its service with `@Optional()` or an optional `inject` entry (`{ token: SmsService, optional: true }`) [di-prefer-constructor-injection, devops-use-config-module]
- [ ] **Critical:** no per-request state in a singleton's field (one caller sees another's data) [di-scope-awareness]
- [ ] The caller arrives as `authUser: JwtUser` and cross-cutting values (the request id) through CLS; `Scope.REQUEST` (or `@Inject(REQUEST)`) only in a provider that wraps a per-request resource, such as a DataLoader [di-scope-awareness]
- [ ] No service locator: no `ModuleRef` lookup of a dependency and no hand-written global container. `moduleRef.resolve(token, contextId)` only for a request-scoped or transient provider, `moduleRef.get()` only on a lazily loaded module, both by a token or a class, never an interface; a choice made per call is a map of every implementation built in a factory provider of the module from injected providers [di-avoid-service-locator]
- [ ] An abstraction is injected through a `Symbol` token or an abstract class, never a string token or an interface type alone; the token (`payment/constants/payment-adapter.constant.ts`), the interface (`payment/interfaces/payment-adapter.interface.ts`) and the binding live in the owning module and stay inside it; the implementation is chosen from config, never from `process.env.NODE_ENV`; test doubles live in `test/` (`FakePaymentAdapter` in `test/helpers/fake-payment-adapter.ts`), swapped in with `overrideProvider()` or a provider of the testing module, and no production module imports one [di-use-interfaces-tokens, arch-resource-naming]
- [ ] Interfaces are small, one capability each and one per file (`NotificationEmailAdapter`, `NotificationSmsAdapter`, each behind its own token); a service injects only the ones it calls, and one that needs two channels injects each [di-interface-segregation]
- [ ] A contract for a call to an outside system names every outcome its caller acts on. For a call that changes something in an outside system (a charge, a transfer, a message sent), those are done, rejected for this input (a declined card, for a payment), refused (nothing happened, and sending it again fails the same way) and unknown (the system may have acted). Every implementation, fakes included, reports each one the same way: one that throws a 500 for a refusal makes the caller treat it as unknown and send it again forever [di-liskov-substitution]
- [ ] Every implementation of an interface passes one shared contract suite (`test/helpers/payment-adapter.contract.ts`): a fake returns the real shape, validates and throws as the real implementation does, and runs the suite in the unit tier; an implementation with an injected client is never constructed by hand, but covered by the module's e2e suite with the SDK mocked by its class (`Stripe`) [di-liskov-substitution]
- [ ] A property only some implementations have (delivered once when sent twice with one key) is declared by each implementation, and the contract suite tests the declared behavior; a fake declares and behaves as the implementation it stands for, never kinder; an unknown outcome is sent again only to a provider that takes an idempotency key, and recorded for a check otherwise [di-liskov-substitution]

## Guards and Authorization
- [ ] `AuthJwtGuard` and then `AuthRolesGuard` registered globally as `APP_GUARD` providers in `AppModule`; routes opt out with `@Public()` and require roles with `@Roles()`; no per-route `@UseGuards` for them (a second registration runs them twice) and no check of `request.user` or roles inside a handler; a protected route left unguarded (no global `AuthJwtGuard`, or `@Public()` on a route that needs a caller) is **Critical** [security-use-guards]
- [ ] `@Public()` and `@Roles()` live in `api/decorators/`, the guards in `auth/guards/`, and the metadata keys are exported constants in `api/constants/` (`API_IS_PUBLIC_KEY`, `API_ROLES_KEY`), never string literals repeated in two files; `AuthRolesGuard` handles a public route and a missing user without a `TypeError`; in an app with a gateway or message handlers, both guards return `true` first for a context that is not HTTP (`context.getType() !== 'http'`), where the gateway and the message controller check their callers themselves [security-use-guards, api-real-time-updates, micro-use-patterns]
- [ ] Ownership is scoped in the service by `authUser.id`, never in a guard; a resource the caller may not see answers the same 404 as a missing one, on every route under it too (a nested route checks that the child belongs to the parent); 403 only for an action a rule forbids on a resource the caller can see. A route that reads or changes another user's item by its `:id` without that scope (`GET /users/:id` answering any account to any customer) is **Critical** [security-use-guards, error-throw-http-exceptions, api-controller-conventions]
- [ ] One passport `AuthJwtStrategy` behind the global guard; its `validate()` builds a complete `JwtUser` (no optional field) or refuses the token with a 401. With a refresh exchange and access tokens of 15 minutes or less it builds it from the claims alone, with no database read per request; without a refresh exchange, or with longer access tokens, it loads the caller by `sub` (one primary-key read) and builds it from the row, so a removed role or a deleted user counts at the next request, and roles read from such a token's claims are a **Warning**; a token the app issues carries nothing beyond what `JwtUser` needs [security-auth-jwt]
- [ ] The strategy verifies signature, expiry, issuer and audience and pins the algorithm (`algorithms: ['HS256']`, and `algorithm: 'HS256'` in `JwtModule`'s sign options), with the key, issuer and audience from the `auth` namespace; with an external identity provider, `secretOrKeyProvider` from `jwks-rsa` and the provider's issuer, audience and algorithm [security-auth-jwt]
- [ ] Access tokens live minutes; refresh tokens the app issues are random, stored as SHA-256 hashes (never a slow password hash, which would prevent the lookup), work once and are revocable [security-auth-jwt]
- [ ] `validate-env.ts` requires `AUTH_JWT_SECRET`, `AUTH_JWT_ISSUER` and `AUTH_JWT_AUDIENCE`, and refuses a secret under 64 characters (the 256 bits HS256 needs, as hex) and an access-token TTL over 60 minutes, so access tokens stay short-lived in every environment [security-auth-jwt, devops-use-config-module]
- [ ] When the app issues its own refresh tokens: the refresh exchange checks the session and the token first, so a token of an ended session is a 401 whatever the account's state; only then it reloads the user: 401 for a missing one and, when the app can disable accounts, 403 `USER_DEACTIVATED` for a deactivated one; the new access token carries the user's current roles; deactivating or deleting a user revokes their sessions, so no refresh token of theirs works [security-auth-jwt]
- [ ] When the app issues its own refresh tokens, a session is one row: refresh updates it first, in its transaction, on the conditions it must meet (not revoked, not expired; `revokedAt IS NULL` and `expiresAt` in the future in the shop), which locks it, then marks the presented token used on the condition that it was unused, and either update changing nothing is a 401; logout and a reused refresh token revoke the session row. Revoking a session's tokens one by one is a **Warning**, since a concurrent refresh's new token survives. The session's end is set once, at login, and a refresh never moves it [security-auth-jwt, db-use-transactions]
- [ ] Rows that grow with use (used refresh tokens, ended sessions) are deleted after a retention kept in the module's `constants/`, by a cleanup the `scheduler/` module calls on an interval; it runs on every instance, so a second run must find nothing more to delete [security-auth-jwt, arch-feature-modules]
- [ ] When the app can disable accounts, the routes that change who may sign in or act (deactivation, email, password, roles) read the caller's row inside the change's transaction, locked with the target's in id order, and refuse a deactivated caller with 403; a check outside the transaction lets two callers acting on each other both pass; a login refuses a deactivated user with 403 `USER_DEACTIVATED` only once the password has matched [security-auth-jwt, security-hash-passwords, db-use-transactions]

## Interceptors and Middleware
- [ ] What applies to every route (the response envelope, request logging) is an interceptor registered once in `ApiModule.setup()`; a timeout goes on the routes that need it; translating errors belongs to the exception filter, and response caching uses `CacheInterceptor` [api-use-interceptors]
- [ ] `ApiModule.setup(app, corsOrigins)`, called by both `main.ts` and `createTestApp()`, registers the security headers and CORS, then the global `ValidationPipe`, the filter and the interceptors, plus the global prefix and versioning. The filter and interceptors are providers of `ApiModule.forRoot()`, taken with `app.get()`, and `AppModule` and every e2e testing module import `ApiModule.forRoot()`; never `APP_PIPE`, `APP_FILTER` or `APP_INTERCEPTOR` providers, which a testing module that does not import them silently runs without [test-use-testing-module, api-platform-agnostic]
- [ ] The global interceptors are listed outermost first: `ApiLoggerInterceptor`, `ApiResponseInterceptor`, then `ClassSerializerInterceptor`, so the envelope wraps the serialized body [api-use-interceptors, api-use-dto-serialization]
- [ ] Successful responses are shaped once, by `ApiResponseInterceptor`: `{ success, statusCode, data }`, and a `PaginatedResult` becomes `data` plus `meta` (`totalCount`, `limit`, `offset`, and `totalCountCapped` when set); a `StreamableFile` and an empty body (`204`) pass through unwrapped [api-use-interceptors]
- [ ] A request log line has the method, the path from `apiRequestPath()` (never the query string), the status and, for a success, the duration in the message, with `userId` and `ip` as fields. `ApiLoggerInterceptor` logs successes only: a guard's refusal and an unknown route never reach it [api-use-interceptors]
- [ ] The global interceptors return `next.handle()` unchanged for a context that is not HTTP, and `ApiResponseInterceptor` also for an `@Sse()` handler (`SSE_METADATA`): wrapped in the envelope, an SSE event reaches the client without its type or id [api-real-time-updates]
- [ ] `ApiTimeoutInterceptor` sits only on routes that read, and its 408 says the answer was not ready in time: rxjs's `timeout` stops the wait, not the handler, so on a route that writes the client is told a write failed that completes; never a global timeout [api-use-interceptors]
- [ ] No business logic in interceptors or middleware

## Error Handling
- [ ] One global `ApiExceptionFilter`, a provider of the api module registered by `ApiModule.setup()`, turns every error into `{ success: false, statusCode, error, message, errorCode }`; no try/catch that formats an error response in a controller, and no second filter per error type. The only scoped filters are the health controller's `HealthUnavailableFilter`, a gateway's `ApiWsExceptionFilter` and a message controller's own filter [error-use-exception-filters, micro-use-health-checks, api-real-time-updates, micro-use-patterns]
- [ ] Every error carries an `errorCode`: the exception's own, read from `getResponse()` (the NestJS 12 `errorCode` option, or the response object on NestJS 11), otherwise the `HttpStatus` name of its status (`NOT_FOUND`), `ERROR` for a status `HttpStatus` does not name [error-use-exception-filters]
- [ ] A client that must tell two errors of one status apart gets an `errorCode` (`UPPER_SNAKE_CASE`, never changed once clients use it), never a message to compare. A domain refusal answered with 400, the status of the route's validation errors, always gets an `errorCode` of its own (`ORDER_NOT_CANCELABLE`, `INSUFFICIENT_STOCK`), or it reads as `BAD_REQUEST`, like every invalid field [error-throw-http-exceptions]
- [ ] An exception with `retryAfterSeconds` in its response object gets a `Retry-After` header in whole seconds from the filter, through `httpAdapter.setHeader()`; the field stays out of the body, and a value that is not a positive integer sends no header [error-throw-http-exceptions, error-use-exception-filters]
- [ ] The filter replies through `HttpAdapterHost` (`httpAdapter.reply()`, `setHeader()`, `getRequestUrl()`, `getRequestMethod()`), never Express's `response.status().json()` [error-use-exception-filters, api-platform-agnostic]
- [ ] The filter reads the message from `exception.getResponse()`, not `.message`, so `ValidationPipe`'s per-field messages survive; `ValidationPipe` keeps the default `errorFormat: 'list'` [error-use-exception-filters]
- [ ] An unknown error answers a generic 500: no stack trace, SQL or driver message in a response; an error translated by hand keeps the original as its `cause` [error-use-exception-filters]
- [ ] The filter translates known non-HTTP errors by code, never by message text: a unique violation (`23505`) to 409; a transaction conflict no helper retried (`40001`, `40P01`) to the retry helper's 409 `TRANSACTION_CONFLICT`; text PostgreSQL cannot store (`22021`, `22P05`) to 400; a domain error class to its status [error-use-exception-filters]
- [ ] A service that names a duplicate itself ("Email already registered") catches the violation of its own index by name (`isUniqueViolation(error, 'UQ_users_email_active')`), never looks the value up first: two concurrent requests both pass the lookup [error-throw-http-exceptions, error-use-exception-filters]
- [ ] Prisma: the filter maps `P2002` to 409 and `P2025` to 404, both with the status's generic message (a `P2025` message names the call and the source file); a service that names its own clash reads the constraint from `meta.driverAdapterError.cause.constraint.index`, since Prisma sets no `meta.target` with a driver adapter [error-use-exception-filters]
- [ ] The filter writes one log line per failed request: a 5xx at error level with the error as pino's `err` field (`{ err: exception }`, the stack and every cause), any other status at warn (with Prisma, a busy database's 503 too, since it is load, not a bug); each with the method, the path without its query string and the status, and `userId` and `ip` as fields [error-use-exception-filters, api-use-interceptors]
- [ ] Every promise in a request is awaited; one left unawaited on purpose has a `.catch()` that logs it as `err` and reports it with `SentryService.reportError()`; work that must eventually succeed goes to a queue instead [error-handle-async-errors]
- [ ] Every `@OnEvent` listener and `@Interval` or `@Cron` method catches its errors, logs them as `err` with the work's id (never the whole event or DTO), reports them with `SentryService.reportError()` and never rethrows. Queue processors and outbox listeners (`@OnOutboxEvent()`) are the exception: they throw, so the job or the event is tried again [error-handle-async-errors, error-report-to-sentry]
- [ ] A WebSocket gateway carries `@UseFilters(ApiWsExceptionFilter)`: global filters do not run on gateways, while the global `ValidationPipe` does, and its 400 would reach the client as "Internal server error". The filter sends an HTTP exception's response object and reports any other error to Sentry [api-real-time-updates]
- [ ] Sentry only through `src/sentry/`: `@sentry/nestjs` is the only Sentry dependency, at one exact version, imported only by `src/sentry/` (`@sentry/nestjs/setup` only by `SentryModule`); every call into the SDK goes through the static methods of `SentryService` [error-report-to-sentry]
- [ ] `src/sentry/preload.ts`, at the Sentry module's root, starts the SDK before the app: every start script runs `node --enable-source-maps --import ./dist/sentry/preload.js` (`--require` in CommonJS; `start:dev` through `nest start --exec`), and the local ones also pass `--env-file-if-exists=.env`; never an import from `main.ts`. `preload.ts` and `SentryService` import nothing from Nest, and `preload.ts` reads `SENTRY_DSN`, `APP_ENV` and `APP_RELEASE` from `process.env` [error-report-to-sentry]
- [ ] `AppModule` imports `SentryModule`, which imports the SDK's `SentryModule.forRoot()` (events named after the route pattern) and calls `SentryService.close()` in `onApplicationShutdown` [error-report-to-sentry]

## Database and Migrations
- [ ] The model is singular and its table plural, named explicitly (`Order` maps to `orders`, `OrderItem` to `order_items`); every table, column, join column, junction table and foreign key is lowercase `snake_case`, and properties are camelCase [db-schema-conventions]
- [ ] Timestamps are `timestamptz`, never `timestamp` without a time zone; structured data is `jsonb`, nullable or with a default when optional; the owning side of a relation keeps its foreign key as a plain property beside the relation (`userId` beside `user`, on `user_id`) [db-schema-conventions]
- [ ] Soft deletes are a nullable `deleted_at` `timestamptz` kept out of responses: deleting sets it, every query skips the rows where it is set, and raw SQL filters `deleted_at IS NULL` itself [db-schema-conventions]
- [ ] A set of values is a native enum type or a `varchar` (`varchar[]` for several), never a `varchar` with a CHECK listing the values; one TypeScript enum with snake_case values (`Pending = 'pending'`) is the list in code [db-schema-conventions]
- [ ] Indexes and constraints are named `IDX_`, `UQ_` or `CHK_`, then the table, then the columns or the purpose (`IDX_orders_user_id_status`, `CHK_orders_total_cents_non_negative`); primary and foreign keys keep the names the ORM gives them [db-schema-conventions]
- [ ] TypeORM: `SnakeNamingStrategy` on every DataSource, the app's and the migration CLI's; `@Entity('orders')` names the table; no column name written by hand except the `@JoinColumn({ name: 'user_id' })` that pins a relation and its plain foreign key column to one column [db-typeorm-schema-conventions]
- [ ] TypeORM: `@CreateDateColumn`, `@UpdateDateColumn` and `@DeleteDateColumn` take `type: 'timestamptz'`, the last nullable and hidden; a soft-deletable row is deleted with `softDelete()` or `softRemove()`, never `delete()` or `remove()`, which remove the row [db-typeorm-schema-conventions]
- [ ] TypeORM: `@Index`, `@Unique` and `@Check` take their `IDX_`, `UQ_` or `CHK_` name as first argument; a changed CHECK expression or partial index condition gets a new name in the same change, since TypeORM matches a CHECK by name only and never compares an index's `where`, so the change generates nothing and the drift check passes [db-typeorm-schema-conventions]
- [ ] TypeORM: ids are `@PrimaryGeneratedColumn('uuid')`, and every DataSource sets `uuidExtension: 'pgcrypto'` and `installExtensions: false`; without them TypeORM writes `uuid_generate_v4()` and runs `CREATE EXTENSION` for `uuid-ossp`, which the drift check does not notice. An extension a column needs (`citext`) is created by hand in the migration that adds the column [db-typeorm-schema-conventions]
- [ ] TypeORM: a native enum column names its type, `@Column({ type: 'enum', enum: OrderStatus, enumName: 'order_status' })` (without `enumName` it is `orders_status_enum`); a `varchar` set is `@Column({ type: 'varchar' })`, with `array: true` for several, typed with the TypeScript enum [db-typeorm-schema-conventions]
- [ ] TypeORM in an ESM project: relation properties are typed `Relation<Entity>`, plain columns never [references/project-setup]
- [ ] TypeORM: the `database/` module owns the connection: it registers `TypeOrmModule.forRootAsync()` (the app's DataSource options live there, never in `app.module.ts`), which `AppModule` imports through it, and provides and exports `DatabaseTransactionService`; the checks that know TypeORM's errors, shared by the filter and the services (`isUniqueViolation()`, `isTransactionConflict()`, `isUnstorableText()`, `isRowLevelError()`), sit in its `utils/`, never in the api module or `src/shared/` [db-typeorm-use-transactions, error-use-exception-filters, arch-shared-folder]
- [ ] Structural migrations (tables, columns, constraints, indexes, foreign keys) are generated by the ORM's CLI from the model change, never hand-written; a hand-written migration only changes data (a backfill, a one-off script) or validates a constraint added `NOT VALID` (`VALIDATE CONSTRAINT`, see `db-use-migrations`). When the CLI could not run, the change has no structural migration file and says first which exact commands are still to run; a hand-written stand-in ("regenerate this") is a finding [db-use-migrations]
- [ ] No schema change outside a migration: no automatic schema sync in any environment, local development included, and no DDL run by the app [db-use-migrations]
- [ ] **Critical:** TypeORM `synchronize` is hardcoded to `false`, never `true` and never read from config [db-typeorm-use-migrations]
- [ ] TypeORM: structural migrations come from `migration:generate`, and `migration:create` only for data changes and for validating a constraint added `NOT VALID`; filenames are lowercase and dash-separated (`{timestamp}-create-order-items-table.ts`), the class PascalCase [db-typeorm-use-migrations]
- [ ] **Critical:** no edit to a migration already applied anywhere but the author's machine: the databases where it ran never get the change, so environments drift apart unnoticed; a fix goes in a new migration [db-use-migrations]
- [ ] Generating again once the migration is applied produces nothing (no drift) [db-use-migrations]
- [ ] **Critical:** a destructive change (a column or table dropped or renamed, a type narrowed, a rename the generator wrote as a drop plus an add) is split into expand and contract across releases, so the release still running during the rollout keeps working; other schema changes are additive (a nullable column, a column with a default, a new table) [db-use-migrations]
- [ ] Expand and contract run over releases, each deployed once the one before runs everywhere: the expand release adds the new columns, writes the old and the new, and trusts the new ones of a row only while they agree with the old one; then one release reads only the new columns, after copying again every row whose new columns are empty or disagree, still writing the old one; then one stops writing the old column, makes it nullable and unmaps it from the model (a model that still maps a column names it in every query); then one drops it [db-use-migrations]
- [ ] A backfill that runs while the previous release still writes works in batches, computes its values from the row it updates in the `UPDATE`'s `SET` (never from a second read of the table joined in, which PostgreSQL does not re-read after waiting for a row lock), and writes only the new columns, never the old one [db-use-migrations]
- [ ] A migration that adds an enum value (`ALTER TYPE ... ADD VALUE`) does not also use it, in a partial index's condition, a default or a backfill; the use goes in the next migration [db-use-migrations]
- [ ] A migration that adds a CHECK or a foreign key to a table that already has rows comes after a data migration that fills the old rows that may break it; on a table that holds many rows it adds the constraint `NOT VALID` and validates it in the next migration (`VALIDATE CONSTRAINT`), so the check does not block writes [db-use-migrations]
- [ ] Migrations are applied by a deploy step of their own that finishes before the new release takes traffic, never by the app at startup, where every replica runs them at once (TypeORM `migrationsRun: true`) [db-use-migrations, db-typeorm-use-migrations]
- [ ] TypeORM: the migration DataSource sets `migrationsTransactionMode: 'each'`; under the default `'all'`, a fresh database applies an enum value and its first use in one transaction, which PostgreSQL refuses. A batched backfill sets `transaction = false` on its class, so each batch's `UPDATE` commits on its own, and updates only the rows still empty, so it can run again [db-typeorm-use-migrations]
- [ ] **Critical:** TypeORM: with `DB_SSL` on, the migration DataSource connects with `ssl: { ca }` (`ca` read from `DB_SSL_CA_FILE`, or Node's own list without it), as the app's DataSource does: without `ssl`, the CLI sends the schema owner's password over a connection without TLS, and `rejectUnauthorized: false` lets any certificate through [db-typeorm-schema-conventions, devops-use-config-module]
- [ ] TypeORM: both DataSources set the same `search_path` (schema first, then `public`) as a startup option (`extra: { options: '-c search_path=...' }`); migration SQL leaves table and index names unqualified, with the schema prefix `migration:generate` emits stripped (`"public"."..."` in `DROP INDEX` and in every enum type) [db-typeorm-use-migrations]
- [ ] TypeORM: a column unmapped before it is dropped keeps its property as `@Column({ nullable: true, select: false, insert: false, update: false })`; removing the property generates the `DROP COLUMN` a release early [db-typeorm-use-migrations]
- [ ] TypeORM: every `down()` works: one that removes enum values drops, and restores by hand with a comment, the column default or partial index condition that names the type; one that cannot put back rows the migration made possible (a `SET NOT NULL` over rows that are now `NULL`) refuses first, with a message saying which rows block it [db-typeorm-use-migrations]
- [ ] **Critical:** writes that must succeed or fail together run in one transaction, and every query inside goes through it; a query through anything else (an injected repository or `this.dataSource` inside `dataSource.transaction()`, `this.prisma` inside `$transaction()`) runs outside and commits on its own [db-use-transactions, db-typeorm-use-transactions, db-prisma-use-transactions]
- [ ] Transactions stay short and touch only the database: no call to an outside system (a payment provider, mail, another service) inside; the transaction commits, then the call runs, and its outcome is recorded in a second write or handed to a queue; a slow transaction is shortened, never given a longer timeout [db-use-transactions]
- [ ] A call that changes something in an outside system (a charge, a transfer, a message sent) keeps its outcomes apart in the record: done; rejected for this input (a declined card: recorded, never sent again, and what it was for stays open for a new call with other input and a key of its own); refused (the provider answered with a refusal and changed nothing: recorded, never sent again); unknown (no answer, a 5xx, an answer the code cannot read: pending; with a provider that takes an idempotency key, sent again with the same key, each wait longer, only while the provider keeps the key; then, or at once with a provider that takes none, marked for a person to check and reported). Outcomes not kept apart are **Critical**: treating every failure as unknown sends a refusal again forever and leaves what it was for stuck; treating every failure as refused loses a charge that went through [db-use-transactions, di-liskov-substitution, micro-use-http-clients]
- [ ] When an outside system reports an outcome later (in the shop, a card payment waiting for 3-D Secure), the call is a pending row: when what it was for ends first, the call is canceled at the provider after the commit, retried from the row; a result reported for something that ended, or that another call already settled, is recorded with its compensating call (a refund for a charge) in the same transaction, and that call is sent after the commit [db-use-transactions]
- [ ] A write to another module's data goes through that module's service; when it must join the caller's transaction, the method takes the transaction as its first parameter (TypeORM `manager: EntityManager`, Prisma `tx: Prisma.TransactionClient`) and uses it for every query; the caller never touches the other module's tables [db-use-transactions, db-typeorm-use-transactions, db-prisma-use-transactions]
- [ ] A change that depends on the current state (a stock level, a balance, a status transition) is one conditional update with the expected state in its criteria, acted on by the number of rows it changed (TypeORM `affected`, Prisma `updateMany` and its `count`); the row is read afterwards only to answer 404 or 400. A read, a check in code, then an update races: Warning, and **Critical** for a read-check-write on a value concurrent requests also change (a balance, a stock level, a quota, a seat count) [db-use-transactions, db-typeorm-use-transactions, db-prisma-use-transactions]
- [ ] A check the change depends on (another row's state, or the caller's own when a route refuses a caller in some state) reads that row inside the change's transaction with `FOR UPDATE`, never before the transaction starts; two such rows are locked in id order [db-use-transactions]
- [ ] An update writes only the request's fields, in one update statement with `deleted_at IS NULL` in its criteria on a soft-deletable model, then reads the row to return it or to answer 404; never a loaded row changed in memory and saved back. TypeORM: never `save()` of a loaded entity to update it (it reloads the row, soft-deleted ones included, writes the stale columns over a concurrent change and undoes a concurrent soft delete), and `update()` does not skip soft-deleted rows, so its criteria include `deletedAt: IsNull()` [db-use-transactions, db-typeorm-use-transactions]
- [ ] A limit checked by a count and then an insert first locks what the limit belongs to: its row (`FOR UPDATE`, TypeORM `lock: { mode: 'pessimistic_write' }`), or, when no row of the module stands for it, a transaction-level advisory lock keyed by the set, the key naming its purpose (`pg_advisory_xact_lock(hashtextextended('order-pending:' || user_id, 0))`); `SERIALIZABLE` only for a check over rows that no one key names [db-use-transactions, db-typeorm-use-transactions]
- [ ] An update over a set of rows that another transaction may be adding to (every token of a session, every item of an order) is guarded by one row that stands for the set, updated both by the transaction that adds to the set and by the one that changes it [db-use-transactions]
- [ ] Transactions that write the same rows lock them in one order: the parent before its children (the order row `FOR UPDATE` before its payments, even when the order is updated last), the rows of one table in the order of their key (an order's inventory items by `sku`), and rows that several parents share in one order of tables across the app; a step written in another order is moved, not left to the deadlock detector [db-use-transactions]
- [ ] A transaction that locks rows other transactions also lock, or runs `SERIALIZABLE`, goes through the transaction service of the module that owns the connection (`DatabaseTransactionService.retried()` or `serializable()` with TypeORM, `PrismaTransactionService` with Prisma), never a retry loop of its own; its work only touches the database, since it runs again on a conflict (SQLSTATE `40001` or `40P01`, on a query or on the `COMMIT`); exhausted attempts answer 409 `TRANSACTION_CONFLICT`, never a 500 [db-use-transactions, db-typeorm-use-transactions, db-prisma-use-transactions]
- [ ] A chunked bulk write falls back to one row at a time, each in its own transaction, for any row-level error (SQLSTATE classes `22` and `23`; `isRowLevelError()` from `database/utils/` with TypeORM, `prisma/utils/` with Prisma), records each refused row's failure with its reason and goes on; any other error (a lost connection, a conflict) fails the chunk for the job to try again. A fallback for one code fails the whole chunk on any other refusal, with nothing reported [db-use-transactions, db-typeorm-use-transactions, db-prisma-use-transactions]
- [ ] **Critical:** values reach SQL as parameters (TypeORM `where('user.email = :email', { email })`), never concatenated or interpolated into the query text [security-validate-all-input]
- [ ] No N+1: related rows load in the same query (a join) or in one batched query for all the rows (`WHERE order_id IN (...)`), never a query per row in a loop; a join or `include` stays inside one module, and another module's rows load in one batched call to its service (`productService.findByIds(ids)`); no relation that loads itself on access in a list a response serializes; a GraphQL field resolver loads through a request-scoped DataLoader [db-avoid-n-plus-one]
- [ ] TypeORM: relations load with `relations` or a query builder join (`leftJoinAndSelect`), with `select` when only some columns are needed; no lazy relation (a `Promise<T>` property) in a list; a paged list pages the parent rows alone (`skip`, `take`, `order` on their own columns) and loads each relation for the page with one `In(ids)` query, since `relations` with `skip`/`take` scans every match and, with an `order` on a relation's column, pages the joined rows (short pages, repeated parents, a wrong `totalCount`) [db-typeorm-avoid-n-plus-one]
- [ ] TypeORM 1.x: find options use the object form of `relations` and `select`; no `null` or `undefined` value in a `where` object, which throws: an optional filter's key is left out, and `NULL` is matched with `IsNull()` [references/project-setup]
- [ ] List endpoints are paginated by offset and return `{ result, totalCount, limit, offset }` (`PaginatedResult`), `totalCount` counting every matching row, not the page, in a stable order whose sort ends on a unique column (`createdAt`, then `id`) [perf-optimize-database]
- [ ] Queries select only the columns the response uses and load only the relations it needs; a count runs in the database, never by loading a relation to count its rows [perf-optimize-database]
- [ ] The columns queries filter and sort on are indexed, the columns a scheduled cleanup deletes by (an expiry, a retention date) included, and every foreign key a query filters or joins on has a plain index: PostgreSQL creates none, and a partial index does not serve an unfiltered join [perf-optimize-database]
- [ ] A text search has an index made for its operator: a plain btree index on a text column (under any collation but `C`) serves no `LIKE` or `ILIKE`, not even a prefix; a prefix search takes a `text_pattern_ops` index, a case-insensitive or substring search a trigram GIN index (`gin_trgm_ops`), whose extension a migration creates [perf-optimize-database]
- [ ] A client's text inside a `LIKE` pattern has its `\`, `%` and `_` escaped (`escapeLike()`), or `?search=%` matches every row: TypeORM's `Like()` and `ILike()` and Prisma's `contains`, `startsWith` and `endsWith` escape nothing [perf-optimize-database, db-prisma-schema-conventions]
- [ ] A public search that matches by text bounds its cost: it ranks only a capped set of candidates, and its total counts at most one row past the cap, reaching the client as the cap with `totalCountCapped: true` in `meta`; the cap is in the module's `constants/` [perf-optimize-database]
- [ ] An overlap check uses the range operator (`&&`) that the exclusion constraint's GiST index serves [perf-optimize-database]
- [ ] The pool size comes from a setting (`DB_POOL_SIZE`: TypeORM's `poolSize`, the `max` of Prisma's adapter pool), and the README states pool size times instances, plus migration and admin connections, against the database's `max_connections` (the pooler's limit behind PgBouncer) [perf-optimize-database]

- [ ] `prisma/schema.prisma` holds only the `generator` and `datasource` blocks; the models live in one `.prisma` file per owning module (`Order` and `OrderItem` in `prisma/order.prisma`), and only that module's services write them; the database URL is in `prisma.config.ts`, never a `url` in the `datasource` block [db-prisma-schema-conventions]

- [ ] Enum values are named as the database stores them, without `@map` (`pending`, with `@@map("order_status")`): `Pending @map("pending")` makes the client read and write `'Pending'`, so the API answers it, `@IsEnum()` accepts only it and a raw `::order_status` cast fails with `22P02`; PascalCase names in code come from a const object whose values are the database's, typed by the generated union [db-prisma-schema-conventions]

- [ ] Indexes and unique constraints are named through `map:` (`IDX_...`, `UQ_...`); a value unique among live rows is a partial unique index (`where: { deletedAt: null }`); a partial index's object form uses only equality, `null` and `not`, and any other condition is `where: raw("...")` written exactly as `pg_indexes.indexdef` prints it back, or the drift check reports the index on every run [db-prisma-schema-conventions]
- [ ] A CHECK constraint, which the schema cannot express, is added by hand to the SQL of the migration that introduces its column, named `CHK_{table}_{purpose}`, and has a database-tier spec [db-prisma-schema-conventions]
- [ ] **Critical:** a sensitive field (a password hash, a token hash, a secret) is added to `PRISMA_OMIT`, the global `omit` of `PrismaService`, in the change that adds the field, and to the database-tier spec's own list of fields that must stay out of results [db-prisma-schema-conventions, api-use-dto-serialization]

- [ ] `PrismaService` extends `PrismaClient` with its options as type arguments (otherwise the omitted fields stay in the result types), runs on `@prisma/adapter-pg` with the `db` namespace's settings (`ssl: { ca }` from `db.sslCa`), sets `omit: PRISMA_OMIT` and `transactionOptions` (`maxWait`, `timeout`) from settings, logs a warning from `onPoolError` and `onConnectionError`, and calls `$disconnect()` in `onApplicationShutdown` [db-prisma-schema-conventions, perf-optimize-database]
- [ ] The pool's startup `options` set the `search_path`, `TimeZone=UTC` (the adapter sends a `DateTime` without its offset, which PostgreSQL reads in the session's zone) and `lock_timeout`; behind a pooler in transaction mode, which drops startup options, they are the database role's settings [db-prisma-schema-conventions]
- [ ] The transaction limits and the lock wait limit are `db` settings that `validate-env.ts` refuses unless they are whole numbers, with the lock wait limit above PostgreSQL's `deadlock_timeout` and below the transaction `timeout` [db-prisma-schema-conventions, db-prisma-use-transactions]
- [ ] `PrismaService` logs queries at `debug`, only when `db.logging` is on, with the query text and its duration; logging `event.params`, which hold the bound values (a password hash, a token), is **Critical** [db-prisma-schema-conventions, devops-use-logging]
- [ ] **Critical:** with `DB_SSL` on, `prisma.config.ts` adds `sslmode=require&sslaccept=strict` to the URL (and `sslcert` for a private CA): with `sslmode=require` alone, Prisma's schema engine checks no certificate and would send the schema owner's password to a server presenting any certificate. The file reads the `DB_*` variables `db.config.ts` reads, with the same `||` fallbacks [db-prisma-schema-conventions, db-prisma-use-migrations]
- [ ] `previewFeatures` include `partialIndexes` and `strictUndefinedChecks`; without the second, Prisma drops a `where` key whose value is `undefined`, so an `updateMany` or `deleteMany` whose id is missing changes every row and a `findFirst` returns another row: **Critical** when a write's `where` takes a value that can be missing [db-prisma-schema-conventions]
- [ ] An optional filter is `query.status ?? Prisma.skip` or a conditional spread, never `undefined`; a write passes the DTO's defined fields (`definedFields(dto)`), never `data: dto`, which holds `undefined` for every optional field the request left out and throws [db-prisma-schema-conventions, db-prisma-use-transactions, arch-data-access-in-services]
- [ ] The sequential form, `$transaction([...])`, is only for independent writes that must commit together, never for a consistent read under the default isolation, since it is no snapshot; a page and its total that must agree run it with `RepeatableRead`; a nested write (a `create` with a nested `create`) is one transaction by itself [db-prisma-use-transactions]
- [ ] A page and its total are two plain queries (`Promise.all` of `findMany` and `count`), never a sequential `$transaction([findMany, count])`, which gives them no common snapshot under `READ COMMITTED` and holds a connection, failing with `P2028` while the pool is busy; the pair runs with `isolationLevel: RepeatableRead` only where the two must agree [perf-optimize-database, db-prisma-use-transactions]
- [ ] A row lock is a raw `SELECT ... FOR UPDATE` through `tx.$queryRaw` (Prisma has no lock option) and an advisory lock goes through `tx.$executeRaw`, both inside the interactive transaction [db-prisma-use-transactions]
- [ ] Every lock wait is bounded by the pool's `lock_timeout`; a transaction that needs another limit sets its own first, with `` tx.$executeRaw`SELECT set_config('lock_timeout', ${value}, true)` `` (`SET LOCAL` takes no bind parameter); the transaction `timeout` is never raised to make a slow transaction pass [db-prisma-use-transactions]
- [ ] A busy database answers 503 with `Retry-After`, logged at warn with no Sentry event: a lock wait past `lock_timeout` (SQLSTATE `55P03`, inside `P2010` on a raw query and `P2039` on a model query) and a transaction that got no connection within `maxWait` (`P2028` without `meta.timeout`), both recognized by `isDatabaseBusy()`; a `P2028` with `meta.timeout`, a transaction that outlived its `timeout`, stays a 500 reported to Sentry [db-prisma-use-transactions, error-use-exception-filters]
- [ ] With Prisma, the transaction service is `PrismaTransactionService` (`retried()`, `serializable()`), which `PrismaModule` exports beside `PrismaService`; its conflict check reads PostgreSQL's code through `postgresErrorCode()`, never `P2034` alone, which misses a deadlock on a raw row lock (`P2010`) and every conflict at `COMMIT` (a rethrown `DriverAdapterError`); `postgresErrorCode()`, `isTransactionConflict()`, `isRowLevelError()` and `isDatabaseBusy()` sit in `prisma/utils/`, never in the api module or `src/shared/` [db-prisma-use-transactions, arch-shared-folder]
- [ ] **Critical:** raw SQL goes through the tagged templates `$queryRaw` and `$executeRaw`, which send values as parameters, never through `$queryRawUnsafe` or `$executeRawUnsafe` with interpolated input [arch-data-access-in-services]
- [ ] An omitted field is read only by a query that opts back in (`omit: { passwordHash: false }` in the credentials lookup) in the owning module's service, which never returns that object; inside a transaction (`tx`, a `Prisma.TransactionClient` parameter) the result types still list the omitted fields, which are `undefined` at runtime, so code there never reads one: passed as a compare-and-swap's expected value, it makes the update unconditional [api-use-dto-serialization, security-hash-passwords]
- [ ] No query awaited inside a loop or a `map` over rows: relations load with `include` or a nested `select`, the children of many parents with one `in` query grouped in memory, counts and sums in the database (`_count` in a `select`, `groupBy` with `_sum`); the `relationJoins` preview is not enabled for this, and no code relies on Prisma batching `findUnique` calls [db-prisma-avoid-n-plus-one]
- [ ] Structural migrations come from `prisma migrate dev --create-only --name <snake_case_name>`, reviewed, applied with `prisma migrate dev`, then `prisma generate`; hand-written SQL in a migration is only for data, CHECK constraints, `NOT VALID` on a constraint over existing rows and its validation, and the extension an index needs (`CREATE EXTENSION IF NOT EXISTS pg_trgm` at the top of the migration that first creates a `gin_trgm_ops` index); the drift check is `prisma migrate diff --from-config-datasource --to-schema prisma --exit-code` [db-prisma-use-migrations]
- [ ] `prisma db push` is never used, not even locally, and no DDL runs at runtime (`$executeRaw` of an `ALTER TABLE`); `prisma migrate reset` runs only against a throwaway local database, and nothing sets `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` in the user's place [db-prisma-use-migrations]
- [ ] An applied migration is never edited, not even one only the author's database has run (`migrate dev` sees the edit by its checksum and asks to reset the database); a mistake is fixed forward, and a rollback is a new migration that reverses the change, since Prisma Migrate has no down migrations [db-prisma-use-migrations]
- [ ] A field unmapped before its column is dropped is made optional and marked `@ignore`, never removed, which generates the drop a release early; a renamed field or model is generated as a drop plus an add, so a rename that keeps the column renames only the Prisma field and keeps `@map("old_column")` [db-prisma-use-migrations]
- [ ] A migration file of plain statements commits each one on its own, and a file containing a `DO` block runs as one transaction: a batched backfill is a file whose only statement is a `DO` block that walks the table in id order, commits after each batch and updates only the rows still empty, so it can run again; a `COMMIT` in a `DO` block beside any other statement fails with `2D000` [db-prisma-use-migrations]
- [ ] A database another tool built moves onto Prisma Migrate through a baseline generated with `prisma migrate diff --from-empty`, plus by hand what the schema cannot express (CHECK and exclusion constraints, extensions, rows the old migrations inserted); the deploy step checks the live schema (the diff, the constraints by name, the old tool's history) before `prisma migrate resolve --applied`, and the old history table stays while a rollback to the old release is possible [db-prisma-use-migrations]

## HTTP Platform (Express / Fastify / Node)
- [ ] A new project uses Fastify unless the user or the spec asked for another adapter, and then the choice is not a finding; a new project on Express or `@nestjs/platform-node` that nobody asked for is a **Warning** (why Fastify is in `references/project-setup.md`); an existing project on Express or the Node adapter is not a finding: there the items about `createFastifyAdapter()` and Fastify plugins apply to the project's own adapter, still built in one place that `main.ts` and `createTestApp()` share. On the Node adapter, the keep-alive timeout is set above the load balancer's idle timeout, and a route taking a body over 100 KB sets its own limit [api-platform-agnostic, references/project-setup]
- [ ] Adapter-specific code lives only in the api module (`createFastifyAdapter()`, `setup()`) and `main.ts`; controllers, guards, interceptors, filters, decorators, middleware and specs use no Express or Fastify API, which compiles on the other adapter and fails at runtime. A new project is on Fastify unless asked for another adapter; an existing one keeps the adapter in its `package.json` [api-platform-agnostic]
- [ ] The adapter is built only by `ApiModule.createFastifyAdapter()`, which `main.ts` and `createTestApp()` both call, and what Fastify takes as an adapter option (`trustProxy`, `multipart`, `genReqId`) is set there, never in `main.ts` alone, so the test apps get it too [api-platform-agnostic]
- [ ] Plugins are registered in `ApiModule.setup()` with the package for the adapter in use (`@fastify/helmet` through `app.register()`, `helmet` through `app.use()` on Express; the same for compression and cookies), never in `main.ts` alone. - [ ] `main.ts` creates the app with `ApiModule.createFastifyAdapter(appConfig().trustedProxies)` (the app's `ConfigService` does not exist yet), calls `ApiModule.setup(app, corsOrigins)` and `HealthModule.listenForShutdown(app)`, then `app.listen()` [api-platform-agnostic, devops-graceful-shutdown]
- [ ] Handlers return values: no `@Res()` with `res.status().json()` or `reply.code().send()`; static status and headers through `@HttpCode()` and `@Header()`, file content through `StreamableFile`; filters and interceptors go through `HttpAdapterHost` [api-platform-agnostic]
- [ ] Requests are typed with the api module's neutral `ApiRequest`, never `Request` from `express` or `FastifyRequest` [api-platform-agnostic]
- [ ] Controller paths use plain segments and `:param`s, no wildcard, optional part or pattern, which Express 5 and Fastify read differently; a param's shape is checked in its DTO [api-platform-agnostic]
- [ ] Middleware is written against Node's `IncomingMessage` and `ServerResponse` (`res.statusCode`, `res.setHeader()`, `res.end()`), which both adapters hand it [api-platform-agnostic]
- [ ] CORS lists `methods` explicitly (`@fastify/cors` allows only `GET`, `HEAD` and `POST` by default); a new `PUT`, `PATCH` or `DELETE` is verified with a preflight (`OPTIONS` with `Access-Control-Request-Method` and `TEST_CORS_ORIGIN`) in the api module's e2e spec, which also checks the security headers [api-platform-agnostic]
- [ ] Uploads on Fastify: `multipart: true` on the adapter in `createFastifyAdapter()`, which registers `@fastify/multipart`; never the plugin's `attachFieldsToBody`, which reads every multipart body into memory under its own file limit, on every route, and hands the DTO an empty upload [api-file-uploads, api-platform-agnostic]

- [ ] A gateway that takes messages limits their rate and checks the sender's role in a guard on the gateway, which runs before validation, so invalid messages count too; the global auth guards and the throttler skip every context that is not HTTP (`context.getType() !== 'http'`) [api-real-time-updates]

## Security
- [ ] `AuthThrottlerGuard` is a global `APP_GUARD` after the authentication guards, with `ThrottlerModule` built from the one `API_THROTTLERS` list in `api/constants/`; it overrides `getTracker()` (the caller's id, otherwise `super.getTracker()`, which counts an IPv6 client by its /64; never `request.ip`) and `throwThrottlingException()` (an `HttpException` with `retryAfterSeconds` from `timeToBlockExpire`, since the library sends only `Retry-After-{name}` for a named throttler), and, in an app with a gateway or message handlers, `shouldSkip()`, which skips every context that is not HTTP [security-rate-limiting, security-use-guards]
- [ ] The throttler counts in memory unless the spec requires limits across instances, and then its storage (`ApiThrottlerStore` in `api/stores/`) is Redis; it counts in the instance's memory when a Redis call fails and stays there for a short delay before trying Redis again, so a hung Redis costs one command timeout per delay, not one per request; the counters' client (`REDIS_CLIENT`) fails a command at once while disconnected (`enableOfflineQueue: false`), has a `commandTimeout` and logs only changes of state; without `REDIS_HOST` the store counts in memory from the start [security-rate-limiting]
- [ ] Endpoints that check a credential, send a message or tell whether an account exists (login, password reset, invitation, sign-up, a route that checks a secret the caller supplies such as a card number or a gift card code) get a `@Throttle()` limit of their own from the module's `constants/`; a route that checks a secret the caller supplies is also limited per account like a login, and a route that lets a caller hold a scarce shared resource before committing to it (a reservation, a hold; in the shop, an unpaid order reserving stock) is limited by count per account; a route that must never be limited takes `@SkipRateLimits()`, never a bare `@SkipThrottle()`, which skips nothing when the throttlers are named [security-rate-limiting]
- [ ] A login is limited per account as well as per address: `AuthSessionService.create()` counts every attempt in the throttler's storage (`getStorageToken()`), keyed by the SHA-256 of the normalized email so Redis holds no email, before checking the password, and answers 429 with `Retry-After` past the limit, to the right password too [security-rate-limiting]
- [ ] The adapter trusts exactly the proxies in `APP_TRUSTED_PROXIES` (`trustProxy` in `createFastifyAdapter()`, `trust proxy` on Express), and an empty list trusts none; `trustProxy: true` or `trust proxy` set to `true` is **Critical** (a client chooses its own address through `X-Forwarded-For` and gets past every per-address rate limit), and never a hop count either (Fastify reads a number as trusting nothing, Express trusts whatever connects directly) [api-platform-agnostic, security-rate-limiting]
- [ ] **Critical:** passwords never stored plain, fast-hashed (MD5, SHA) or encrypted [security-hash-passwords]
- [ ] Passwords hashed by one non-exported `UserPasswordHasherService`: Argon2id (Node's built-in `crypto.argon2()` in a new project, the `argon2` package where the project already uses it), or bcrypt (native package, cost 12 or more, `@IsByteLength(1, 72)`) only in a project already on bcrypt; login answers an unknown email and a wrong password with the same 401 [security-hash-passwords]
- [ ] `UserPasswordHasherService` uses the async API (`crypto.argon2()`, never `argon2Sync()`) and explicit Argon2id parameters, at least the OWASP minimum (19 MiB, 2 passes, parallelism 1: `memory` and `passes` in `crypto.argon2()`, `memoryCost` and `timeCost` in the package) and never lowered; with `crypto.argon2()` it stores the PHC string (`$argon2id$v=19$m=...`) with a random salt of at least 16 bytes and compares the derived key with `timingSafeEqual()`, never `===`; it verifies an unknown email against a dummy hash and rehashes when `needsRehash()` says so; its `verify()` catches a hash it cannot parse and returns `false` (401, not 500), logging a fixed message without the error [security-hash-passwords]
- [ ] A rehash or any write that replaces a value read earlier keeps that value in the update's criteria [security-hash-passwords, db-use-transactions]
- [ ] Emails are normalized (`trim().toLowerCase()`) the same way in the sign-up and login DTOs, and a login change that starts normalizing ships with a data migration for the stored rows [security-hash-passwords]
- [ ] When a user can change their password, the change requires the current password and revokes the user's other sessions in its own transaction, never through an event that runs after it; a login checks again, in the transaction that creates its session and with the user's row locked, that the hash it verified is still the user's [security-hash-passwords]
- [ ] When a user can change their email, the change requires the current password, notifies the owner through a channel the change does not control (in the shop, a mail to the old address) and is rate-limited like sign-up [security-hash-passwords]
- [ ] If the app offers a password reset: the token is at least 32 random bytes, stored as its SHA-256, single use within a short lifetime, never in a query string (the shop puts it in the URL's fragment, `#token=`), and its page is `https`; the reset sets the password and revokes every session in one transaction; a reset, an email change and a password change use up the user's open links; the mail job's attempts fall within the link's lifetime; asking for a link answers 202 whether or not the email exists, and is rate-limited per address and per email [security-hash-passwords, security-rate-limiting]
- [ ] Rich-text fields sanitized in the DTO with an allow-list (`sanitize-html`), and only text within the field's `@MaxLength`: longer text passes on for validation to refuse, since sanitizing it first lets one oversized body hold the event loop; plain-text fields stored as sent, never run through `sanitize-html`, which would encode `&` and `<` [security-sanitize-output]
- [ ] Error messages echo only validated values (a UUID from a param DTO), never free text from the client; the `ValidationPipe`'s own messages are the one exception [security-sanitize-output]
- [ ] helmet (`@fastify/helmet` on Fastify) sets a Content Security Policy, and CORS allows only the origins in `app.corsOrigins` [security-sanitize-output, api-platform-agnostic]
- [ ] A route that returns HTML builds it from escaped values; HTML a front end fetches and shows in a frame (`srcdoc`, a `blob:` URL) gets none of its response's Content Security Policy, so the API docs state the rendering contract (an `<iframe sandbox>` without `allow-scripts` or `allow-same-origin`), or the route returns data [security-sanitize-output]
- [ ] A mail to an address nobody has verified carries no text its sender chose (no sign-up name in a welcome mail) [security-sanitize-output]
- [ ] Secrets only in the environment, read through config, and a secret in code is **Critical**; `process.env` read only in `src/config/`, the migration DataSource or `prisma.config.ts` (the `DB_*` variables alone) and `src/sentry/preload.ts`, or for a value read before `ConfigModule` exists or one that must not get the config file's default, with a comment saying why. Test code reads only the variables the tests alone use (`INTEGRATION_API_URL`); a test helper that reaches the app's database, Redis or S3 builds its connection from the app's mapping (the `registerAs` factory called directly, the migration DataSource), never from that server's variables with defaults of its own [devops-use-config-module]
- [ ] A variable holding a secret ends in `_KEY`, `_SECRET`, `_PASSWORD` or `_TOKEN`, and one holding a URL that may carry credentials in `_URL`; a secret named otherwise reaches Sentry and the logs unredacted [devops-use-config-module, error-report-to-sentry]
- [ ] `validate-env.ts` refuses, everywhere but `APP_ENV` `dev`: a URL that receives credentials or personal data unless it is `https`, `DB_SSL` other than `true`, and `REDIS_TLS` other than `true` when `REDIS_HOST` is set [devops-use-config-module]
- [ ] A managed service's own CA is named by `DB_SSL_CA_FILE` or `REDIS_TLS_CA_FILE`, read by the config file and passed as `ssl: { ca }` or `tls: { ca }`, so the certificate is still checked; never `rejectUnauthorized: false` [devops-use-config-module]
- [ ] Input never chooses the host of an outgoing call: it goes in `params` and in path segments encoded with `encodeURIComponent`; a provider's key comes from the client's registration (a header), never the URL, which every log of the call keeps [micro-use-http-clients]
- [ ] Provider reasons that help an attacker (a decline code saying a card is reported stolen) never reach the client: the adapter maps them to a short set the customer can act on and keeps the provider's code in a column no response shows [micro-use-http-clients]
- [ ] A URL a customer gives is validated in the DTO (`@IsUrl({ protocols: ['https'], require_protocol: true })`) and called through the client's own `http` and `https` agents, never the global agent, whose `lookup` checks every resolved address (an IP literal is checked before the call, since Node skips the lookup for it); with `proxy: false`, `maxRedirects: 0`, a deadline for the whole call (`AbortSignal.timeout()`), `maxContentLength`, 6to4, NAT64 local-use and site-local IPv6 among the blocked ranges, and one `unreachable` code for the customer, the precise reason only in the log [micro-use-http-clients, security-validate-all-input]
- [ ] When the app delivers to a customer's system (a webhook), each delivery is signed with an HMAC-SHA256, keyed with the webhook's secret, over a timestamp and the exact body bytes sent, with a fresh timestamp on each attempt and the same delivery id, and the receiver's documentation tells it to compare in constant time and refuse an old timestamp; the header names and the registration flow are the project's own (the shop's: `X-Shop-Signature: t=<unix seconds>,v1=<hex>`, the secret shown once at registration) [micro-use-http-clients]
- [ ] A transport between services authenticates the connection: mutual TLS over TCP (the listener requires and verifies the caller's certificate, `requestCert` and `rejectUnauthorized` on, and the client presents its own), and on a broker a TLS connection with credentials of the service's own, limited to its queues or subjects; no credential in a message's payload; the global HTTP guards skip every context that is not HTTP, which is safe only because the connection is authenticated; message handlers declare their own `ValidationPipe`, exception filter and logging interceptor [micro-use-patterns]
- [ ] A queue dashboard mounted on the platform brings what Nest's globals do not give it: authentication on every request of its scope (the page, its files and its API) in a hook; an error handler answering in the API's error shape, logging the error as `err` and reporting a 5xx to Sentry; a log line per request with the method, the path without its query string, the status, and the caller's id and address as fields; a rate limit counted per caller id, or per `normalizeIp(request.ip)` for an anonymous request [micro-use-queues]
- [ ] A dashboard opened in a browser authenticates with a credential the browser sends by itself, such as a session cookie (`HttpOnly`, `Secure`, `SameSite=Strict`, its `Path` the dashboard's); when a credentialed call from the front end sets it (the shop's flow), that call needs CORS `credentials: true` with the origins still an allowlist and a front end on the same site, stated in the API docs and checked by an integration test sending the credentialed preflight; the dashboard is read-only (`readOnlyMode: true`) when workers claim records by status, a retry going through a route of the record's own module [micro-use-queues]

## Performance
- [ ] Caching only for data that is expensive to compute and read far more often than it changes; every entry has a key that names exactly what it holds and the shape it holds it in (a release that changes that shape, a new API version included, changes the key), a TTL in milliseconds, and an invalidation path [perf-use-caching]
- [ ] The write that changes cached data deletes its keys, in the service method or in a listener for the change event; data read often and changed while read (a public list, its pages) is invalidated by a version read before the rows are loaded, not by deleting its key, and a failed version write is remembered and written at the next read [perf-use-caching]
- [ ] **Critical:** `CacheInterceptor` only on routes whose response is the same for every caller (it keys by URL); caller-dependent data is cached in the service, with the caller in the key; `@UseInterceptors(CacheInterceptor)` on a service method does nothing [perf-use-caching]
- [ ] **Critical:** cached entities are rebuilt with `plainToInstance` (service) or `@SerializeOptions({ type })` (`CacheInterceptor` route returning one entity or an array; a paginated route is cached in the service); a cache hit returned as a plain object skips `@Exclude()`. With Prisma, a hit goes through the route's response DTO (`excludeExtraneousValues: true`) as a fresh result does, and a query that opts back into an omitted field is never cached [perf-use-caching]
- [ ] Several instances share one store (Redis); only an app without queues falls back to a bounded memory store when `REDIS_HOST` is not set, with a warning at startup [perf-use-caching]
- [ ] The Redis store runs on the app's `REDIS_CLIENT` (`CacheRedisStore` in `cache/stores/`), never `@keyv/redis`; the app builds its Keyv with `throwOnErrors: true` and a namespace; a failed cache write makes the service read from the database, leave the cache alone for a while and warn once, tested with the real store against a closed port and a peer that never answers, not with a mock that rejects [perf-use-caching]
- [ ] Cache keys built from client input come from a small, fixed set (the first pages at the default size, without search or filters), named in the API docs; every other query reads the database, so no client can add entries at will [perf-use-caching]
- [ ] No write that any caller can make (a review, a like) invalidates a cache that every caller shares; the data it changes may lag by the cache's lifetime there, documented, and is current where it is read uncached; administrators' writes still invalidate at once [perf-use-caching]
- [ ] A list kept in an instance's memory keeps ids and reads the rows by primary key per request [perf-use-caching]
- [ ] Lifecycle hooks return or await their async work; constructors are synchronous, with no I/O; nothing relies on the order of other modules' `onModuleInit`, and work that uses another module's service runs in `onApplicationBootstrap`; clients and connections close in `onApplicationShutdown`, never in a signal handler [perf-async-hooks]
- [ ] A warm-up the app can serve without never stops the startup: a failure is logged and reported, retried with a growing delay, and the route it feeds answers 503 with `Retry-After` until the first success, never an empty list; readiness stays up. Startup work the app cannot serve without still fails the startup [perf-async-hooks]
- [ ] A module is lazy-loaded only when it is heavy and rarely used, where startup time matters (serverless, a command line), and only when it has no controllers, gateways or resolvers, whose routes would never be registered [perf-lazy-loading]
- [ ] A lazily loaded module's classes are imported dynamically with it, or resolved by a token from a file that imports nothing heavy, never imported statically; the load's promise is shared by concurrent first calls and forgotten after a failure; a test asserts the heavy library stays unloaded until first use, through a mock that records its loading, not by counting `LazyModuleLoader` calls [perf-lazy-loading]

## Code Style
- [ ] No comment says what the code or a name already says: a narration of what a line or block does (`// Find the user`), a restated name, type or column type (`@param id the id`, `// Largest value a PostgreSQL integer column holds` above `PG_INTEGER_MAX`, `// Stored as timestamptz` above a `timestamptz` column), or a convention the rules already state (`// Hardcoded, never from config`). Report one finding per file listing its lines, not one per comment [style-code-comments]
- [ ] No comment describes another file or another class's behavior (`// Called by AuthSessionService for POST /auth/login`, `// Shared by main.ts and test/helpers/create-test-app.ts`): it goes stale when that file changes. A reason may say that other modules depend on the code, without naming them or saying what they do [style-code-comments]
- [ ] No comment records history or the moment of writing: what changed, or why the previous version was wrong (`// Fixed the race`, `// Added for PR #212`), and reasons that hold only until a later change (`// Before the outbox existed ...`, `// There are no write routes yet`, `// New`, `// Temporary`); those go in the commit message, the PR description or a `TODO`. A TODO carries a ticket and a concrete action (`// TODO(SHOP-412): replace the polling with the provider's webhook`) [style-code-comments]
- [ ] Every claim a comment makes holds for this project and this code: a statement about a library, its version or the test runner that is false here, or a comment that no longer matches the code beside it, is a defect, since the reader trusts it. A comment that contradicts the code is a Warning on its own; a change updates or deletes every comment about the code it changes [style-code-comments]
- [ ] No comment copied from a skill example whose reason does not hold in this code, and no line that only names the file (`// order/services/order.service.ts`), which in an example only shows where the code goes [style-code-comments]
- [ ] No commented-out code, section banners (`// ===== Helpers =====`) or a comment on every member of a class; a comment that stays says why (a reason from outside the code, a subtle invariant, an algorithm's approach with its source, a workaround with its issue link and the condition for removing it), short, on its own line above the code it explains [style-code-comments]
- [ ] Private methods, and only private methods, take the `_` prefix and keep the `private` keyword; no prefix on public or protected methods, injected dependencies (`private readonly orderRepository`), other properties, functions, constants, parameters or locals; an unused parameter keeps a plain name (`(label, body) => ...`, never `_label`) [style-private-underscore-prefix]
- [ ] No em dash anywhere: code, comments, string literals, error messages, Swagger descriptions, docs, READMEs, commit messages and the PR description [style-no-em-dash]
- [ ] US-English spelling in identifiers, comments, string literals, error messages, Swagger descriptions, docs, commit messages and the PR description (`canceled`, `behavior`, `serialize`); only a name the project does not control (a third-party field or option) keeps its own, behind a wrapper with US spelling [style-us-english]
